Kubernetes, from the inside out

For engineers who already shell into pods with k9s and now want to know what is actually happening underneath. It covers the machinery, workloads, networking, storage, security, operations, k9s itself, and the distributed-systems ideas that hold all of it together. Each chapter ends with exercises for a cluster you run yourself.

$ kubectl get deployment checkout
NAME       READY   UP-TO-DATE   AVAILABLE   AGE
checkout   2/3     3            2           41d

Almost everything in this guide is about the gap in that one column: what you asked for, what exists right now, and the machinery that keeps closing the difference.

Part I

The machine

01

Why Kubernetes exists

Kubernetes is a system for keeping the state of a fleet of machines equal to a description you wrote down. Once that sentence makes sense, most of its design stops looking arbitrary.

The problem it replaced

Before orchestrators, running a service meant choosing a machine for it. Someone decided that the payments API lives on app-07 and app-08, wrote that down in an inventory file or a wiki, and configured a load balancer to point at those two hosts. When app-07 died at 3 a.m., a person woke up and made the decision again by hand: pick a new host, install the runtime, copy the config, update the load balancer.

Every piece of that is a decision a computer can make better than a tired human: which machine has room, how to start the process, how to find it afterwards, and what to do when it disappears. Google ran this way internally for years with a system called Borg, and Kubernetes (open-sourced in 2014, 1.0 in 2015) is the public descendant of the lessons from Borg and its successor Omega.

Declarative, not imperative

The single most important idea: you do not tell Kubernetes what to do. You tell it what you want, as data, and it works out the steps.

An imperative instruction is “start three copies of this container on these hosts.” If one copy crashes after you issue the instruction, the instruction is still finished; nobody is responsible for the crash. A declarative statement is “there should be three copies of this container.” That statement stays true or false over time, and something has to keep checking it.

That something is a controller, and every controller in Kubernetes runs the same loop:

for {
    desired := readSpec()        // what the user asked for
    actual  := observeWorld()    // what exists right now
    if actual != desired {
        takeOneStepTowards(desired)
    }
    writeStatus(actual)          // report what we saw
}

This is called reconciliation. Self-healing, rolling updates, autoscaling, attaching storage, programming load balancers: all of them are some controller running this loop against some kind of object. When your pod is deleted and comes back, nothing special happened. A ReplicaSet controller noticed that two is not three.

Mental model

Think of the cluster as a database of intentions plus a crowd of small robots. Each robot watches one kind of record, compares it with reality, and nudges reality. No robot knows the whole plan. The plan is the data.

What you get from that design

Because the desired state is data stored in one place, a lot of features fall out almost for free:

  • Scheduling. You state what a workload needs (CPU, memory, constraints). The scheduler decides where it runs. Machines become interchangeable capacity.
  • Self-healing. If reality drifts (a process crashes, a node vanishes), the next pass of the loop notices and corrects it.
  • Service discovery. Workloads move and change IPs constantly, so Kubernetes gives groups of them a stable name and address.
  • Rollouts and rollbacks. Changing the description (a new image tag) is a change of desired state. A controller walks the system from old to new under rules you set.
  • A uniform API. Everything, from a pod to a load balancer to a certificate, is an object with the same shape, read and written through the same API. That uniformity is why tools like k9s can show you any resource type without special code.

The contract you sign

Kubernetes is not magic, and it does not make software reliable on its own. It offers a deal: it will keep the right number of copies running and route traffic to the healthy ones, and in return your application has to accept some rules. Engineers who struggle with Kubernetes are usually breaking one of these without knowing it.

Kubernetes promisesYour application promises
To restart or replace failed instancesIt can be killed at any moment and started somewhere else
To send SIGTERM and wait before killingIt handles SIGTERM by finishing in-flight work and exiting
To route traffic only to instances that say they are readyIt tells the truth about readiness through a probe
To place it on a node with the resources it asked forIt asks for realistic resources and stays within its limits
To give it a stable name to find its peersIt never relies on a specific IP address or host
To keep state on attached volumes, if you askEverything not on a volume can be lost on restart

What Kubernetes is not

It is not a platform-as-a-service. It does not build your code, does not know what a “release” is in your company, and has no opinion on logging or CI. It is closer to an operating system kernel for a cluster: primitives for running processes, networking them, and giving them storage and identity. Platforms are built on top of it, which is why every company’s Kubernetes setup looks a bit different.

It is also not one program. It is a set of cooperating components that talk only through an API. That is the subject of chapter 3.

Exercises

You need the lab cluster from chapter 23 for the second one. The first is a thinking exercise for your work cluster.

  1. Pick one service you run at work. Write down, in one sentence each: the object that holds its desired state, the controller that acts on that object, and what “actual state” that controller observes. Do the same for the Service object in front of it.
    Show a worked example

    For a typical web API: the desired state lives in a Deployment (image, replica count, pod template). The Deployment controller reconciles it by managing ReplicaSets; the ReplicaSet controller observes the number of matching pods and creates or deletes pods. For the Service, the EndpointSlice controller observes which ready pods match the Service’s selector and writes their IPs into EndpointSlice objects, and kube-proxy on every node observes those and programs packet-forwarding rules. Four controllers, none of which know about each other.

  2. Create a deployment with three replicas and watch the reconciliation loop work. In one terminal run kubectl get pods -w; in another, delete one pod. 
    kubectl create deployment hello --image=nginx:1.27 --replicas=3
kubectl get pods -l app=hello -w          # terminal 1
kubectl delete $(kubectl get pod -l app=hello -o name | head -1) --wait=false   # terminal 2
    What to notice

    A new pod with a different random suffix appears before or while the old one is still Terminating. The ReplicaSet does not count terminating pods toward its replicas, so it creates a replacement immediately. That is level-triggered reconciliation: it did not “react to a deletion event,” it observed that only two live pods matched and three were wanted.

Next: Containers, really

02

Containers, really

A container is not a small virtual machine. It is an ordinary Linux process that has been given a restricted view of the system and a restricted budget of resources. Kubernetes is, at the bottom, a very elaborate way of starting such processes.

A process with blinkers on

Run ps aux on a Kubernetes node and you will find your application processes there, owned by the same kernel as everything else. What makes them “containers” is two kernel features applied when they start.

Namespaces control what a process can see. Each kind of namespace isolates one kind of resource:

NamespaceIsolatesEffect inside the container
pidProcess IDsYour app sees itself as PID 1 and cannot see host processes
netNetwork interfaces, routes, ports, iptablesIts own eth0, its own localhost, its own port space
mntMount pointsIts own root filesystem built from the image
utsHostnameThe hostname is the pod name
ipcShared memory, semaphoresNo accidental sharing with other workloads
userUser and group IDsRoot inside can map to an unprivileged user outside (opt-in in Kubernetes)
cgroupView of the cgroup treeSees its own cgroup as the root

Control groups (cgroups) control how much a process can use. Modern nodes use cgroup v2, a single hierarchy where each container gets a directory with files such as cpu.max, cpu.weight, memory.max and memory.current. When you set resource limits in a pod spec, the kubelet eventually turns them into numbers written to these files. Chapter 7 shows exactly how, because the behaviour at the limit (throttling for CPU, killing for memory) explains a large share of production incidents.

Images: layers, digests, tags

An image is a stack of filesystem layers plus a small JSON config (entrypoint, environment, working directory, user). Each layer is a tarball of the changes made by one build step. The runtime stacks them with an overlay filesystem and adds one writable layer on top for the running container. That writable layer disappears when the container is removed, which is why anything you write outside a volume is gone after a restart.

Images follow the OCI (Open Container Initiative) specification, so any compliant runtime can run any compliant image. Every layer and every manifest is addressed by the SHA-256 hash of its content, a digest such as sha256:3f8a…. A digest is immutable: the same digest is the same bytes forever.

A tag like myapp:1.4.2 or myapp:latest is just a mutable pointer to a digest. Someone can push a different image under the same tag tomorrow. This matters in Kubernetes because two nodes pulling the “same” tag a day apart can end up running different code. Chapter 19 comes back to this.

A tag can also point to an image index, a list of per-architecture manifests (amd64, arm64). The runtime picks the one matching the node. If your image only exists for amd64 and lands on an arm64 node, the container fails with exec format error.

The runtime chain

The kubelet does not start containers itself. It talks gRPC to a container runtime through the Container Runtime Interface (CRI). The usual stack today:

kubelet
  └─ CRI (gRPC over a unix socket)
       └─ containerd  (or CRI-O)        pulls images, manages snapshots
            └─ containerd-shim-runc-v2  one per pod, keeps containers alive if containerd restarts
                 └─ runc                 sets up namespaces + cgroups, execs your process, exits

Kubernetes removed its built-in Docker support (“dockershim”) in v1.24. Images built with Docker still run everywhere, because they are OCI images. Only the daemon on the node changed.

The pause container

Before any of your containers start, the runtime creates a pod sandbox: a tiny process (usually called pause) whose only job is to hold the pod’s network namespace (and optionally IPC and PID namespaces) open. Your containers are then started inside those namespaces. This is why all containers in a pod share one IP address and one localhost, and why two containers in the same pod cannot both listen on port 8080. If your app container crashes and restarts, the sandbox survives, so the pod keeps its IP.

PID 1 and signals

Inside its PID namespace, your entrypoint process is PID 1, and Linux treats PID 1 specially: signals with no handler installed are ignored instead of taking their default action. A process that never registered a SIGTERM handler will not die on SIGTERM when it is PID 1. Kubernetes then waits out the whole grace period (30 seconds by default) and sends SIGKILL. Every deploy gets 30 seconds slower and in-flight requests are cut off rather than drained.

The classic way to cause this is the shell form of a Dockerfile command:

# shell form: /bin/sh -c "node server.js" becomes PID 1; sh does not forward SIGTERM
CMD node server.js

# exec form: node is PID 1 and receives SIGTERM directly
CMD ["node", "server.js"]

If you need a shell wrapper, end it with exec your-binary so the shell replaces itself. If your app spawns children it does not reap, run a minimal init such as tini as PID 1.

Pitfall

“Pods take exactly 30 seconds to terminate” is a symptom, not a property of Kubernetes. It almost always means PID 1 is ignoring SIGTERM. Check the entrypoint before tuning grace periods.

Exercises

Use the kind cluster from chapter 23. kind nodes are Docker containers, so you can step inside a node and look at the real runtime.

  1. Open a shell on a node and list what the runtime sees.

    Hint

    The cgroup path includes the pod’s QoS class (a besteffort or burstable slice, or directly under the kubepods slice for Guaranteed pods) and the pod UID.   3. Prove the PID 1 problem. Run a pod whose command is a shell loop without signal handling, delete it, and time the deletion. Then add a trap and compare. 
    kubectl run sleeper --image=busybox:1.36 -- sh -c 'while true; do sleep 1; done'
time kubectl delete pod sleeper

time kubectl delete pod sleeper2
    Expected result

    The first takes about 30 seconds: sh is PID 1 with no TERM handler, so the signal is ignored until the kubelet sends SIGKILL. The second exits within about a second because the trap handles the signal.

Next: Control plane and nodes

03

Control plane and nodes

A cluster is a handful of programs that never call each other directly. They all read and write objects through one API server and react to what they see there. Learn the cast, then follow one request through all of them.

The control plane

kube-apiserver

A stateless HTTP server that is the front door for everything. It authenticates the caller, checks authorization, runs admission plugins, validates the object, and persists it to etcd. It also serves watches: long-lived streams of changes that every other component uses to learn about the world. Because it holds no state of its own, you can run several replicas behind a load balancer.

etcd

A distributed, strongly consistent key-value store that holds every object in the cluster. It uses the Raft consensus protocol, which is why control planes run three or five etcd members rather than two or four (chapter 20 does the quorum maths). If etcd loses its data and you have no backup, the cluster has forgotten everything it was supposed to be running.

kube-scheduler

Watches for pods with no node assigned (spec.nodeName empty), picks a node for each, and records the decision by creating a Binding. That is all it does. It never starts anything. If the scheduler is down, new pods simply stay Pending.

kube-controller-manager

One binary running dozens of independent controllers: Deployment, ReplicaSet, StatefulSet, DaemonSet, Job, CronJob, EndpointSlice, Namespace (cleans up deleted namespaces), node lifecycle (notices dead nodes), ServiceAccount, garbage collector, and more. Each is a reconciliation loop over its own kind of object. When you run several control-plane replicas, only one controller-manager is active at a time; they elect a leader through a Lease object.

cloud-controller-manager

The controllers that need to talk to a cloud provider: creating load balancers for type: LoadBalancer Services, labelling nodes with their zone and instance type, and deleting Node objects when the VM is gone. On a bare-metal or kind cluster it may not exist at all.

The node

kubelet

The agent on every node, and the component that actually makes pods real. It watches the API server for pods bound to its node, asks the container runtime to create sandboxes and containers, mounts volumes, runs liveness/readiness/startup probes, enforces node-pressure eviction, and reports pod and node status back. It also renews a Lease in the kube-node-lease namespace every few seconds as a heartbeat.

The kubelet can also run static pods: manifests in a directory on the node (usually /etc/kubernetes/manifests) that it runs without asking the API server. That is how kubeadm-style clusters run the control plane itself. The API server, scheduler and controller-manager are static pods; you see read-only “mirror pods” for them in kube-system.

Container runtime

containerd or CRI-O, reached through the CRI as described in chapter 2.

kube-proxy

Watches Services and EndpointSlices and programs the node’s packet-forwarding rules (iptables, nftables or IPVS) so that traffic to a Service’s virtual IP reaches a real pod. Some network plugins, notably Cilium, replace kube-proxy with eBPF programs. Chapter 9 covers this in detail.

CNI plugin

Gives each pod a network interface and IP address when its sandbox is created, and makes pod IPs routable across nodes. Usually runs as a DaemonSet plus a binary the runtime calls.

Under the hood

There is one important exception to “everything talks to the API server.” For kubectl logs, exec, attach and port-forward, the API server opens a connection to the kubelet on port 10250 and streams the data through. That is why kubectl get pods can work while kubectl logs on the same pod times out: the control plane can reach etcd but not that node. k9s uses the same path when you press l or s.

The life of kubectl apply

Follow one Deployment from your terminal to a running process. This sequence is worth knowing cold; most debugging is figuring out which step stopped.

  1. Client side. kubectl reads your kubeconfig, picks the current context, loads credentials, and discovers which API group and version serve Deployment. It sends a PATCH (server-side apply) or a GET-then-PATCH (client-side apply) to /apis/apps/v1/namespaces/shop/deployments/checkout.
  2. Authentication. The API server works out who you are from a client certificate, a bearer token, or an OIDC token.
  3. Authorization. RBAC checks whether that identity may patch deployments in shop. A failure here is a 403 Forbidden.
  4. Mutating admission. Plugins and webhooks may change the object: set defaults, inject a sidecar, add labels.
  5. Schema validation. The object is checked against the Deployment schema. Typos in field names are rejected here (with server-side field validation) instead of silently ignored.
  6. Validating admission. Policies may reject the object outright: “images must come from our registry,” “no privileged containers.”
  7. Persistence. The object is written to etcd. Its resourceVersion changes, and because the spec changed, metadata.generation is incremented. Your kubectl command returns here. Nothing is running yet.
  8. Deployment controller. Its watch fires. It hashes the pod template, sees no ReplicaSet with that hash, and creates one (or scales an existing one) according to the rollout strategy.
  9. ReplicaSet controller. Sees a ReplicaSet wanting 3 pods with 0 existing, and creates 3 Pod objects. They have no node yet.
  10. Scheduler. Sees 3 unscheduled pods, filters and scores nodes, and binds each pod to a node.
  11. kubelet. On each chosen node, the kubelet sees a pod bound to it. It pulls the image if needed, mounts volumes, asks the runtime for a sandbox (the CNI plugin assigns an IP), runs init containers, then starts the app containers.
  12. Probes and status. The kubelet runs startup and readiness probes and writes the pod’s conditions back. When Ready becomes true…
  13. EndpointSlice controller. …adds the pod IP to the Service’s EndpointSlices as ready, and kube-proxy on every node updates its rules. Traffic starts flowing.

Thirteen steps, at least six independent actors, and no step calls the next one. Each actor only watches for the change made by the previous one. This is the choreography style of distributed systems, as opposed to orchestration by a central coordinator, and it is why Kubernetes is resilient: if the scheduler restarts mid-way, it just lists unscheduled pods again and carries on.

In production

On managed Kubernetes (EKS, GKE, AKS) you never see the control plane machines; the provider runs etcd and the API server for you. You still own everything on the node side and every controller you install. Knowing the components is what lets you tell “the platform is broken” apart from “my add-on is broken.”

Exercises

These are on the kind lab cluster, where you are allowed to break the control plane.

  1. See the API calls behind a command. Raise kubectl’s verbosity and read the HTTP requests it makes.

kubectl get pods -v=8          # adds request and response bodies (truncated)

  3. Stop the scheduler and observe the consequence. Move its manifest out of the static pod directory, create a pod, then put it back. 
    docker exec lab-control-plane mv /etc/kubernetes/manifests/kube-scheduler.yaml /root/
kubectl run orphan --image=nginx:1.27
kubectl get pod orphan -o wide          # Pending, NODE is <none>
kubectl describe pod orphan             # no events at all: nobody has looked at it
docker exec lab-control-plane mv /root/kube-scheduler.yaml /etc/kubernetes/manifests/
    What to notice and why

    With the scheduler gone, the pod has no events, not even a FailedScheduling one, because no component is responsible for it. Seconds after the manifest returns, the kubelet restarts the scheduler, which lists unscheduled pods and binds orphan. Nothing had to “retry”; the scheduler just reconciled current state when it came back.

  4. Bypass the scheduler entirely. Create a pod that already has spec.nodeName set. 
    apiVersion: v1
kind: Pod
metadata:
  name: pinned
spec:
  nodeName: lab-worker2
  containers:
    - name: app
      image: nginx:1.27
    Why this works, and why you should rarely do it

    The scheduler only acts on pods without a node. A pod with nodeName preset goes straight to that node’s kubelet. It also skips every scheduling check: resource fit, taints, affinity. If the node is full, the kubelet rejects the pod at admission (OutOfcpu, OutOfmemory) and it fails. DaemonSets used to work this way; they now use node affinity and go through the scheduler like everything else.

Next: The API is the product

04

The API is the product

Every feature of Kubernetes is an API object with the same shape and the same rules. Learn those rules once and you can reason about resources you have never seen before, including the custom ones your platform team installed.

Resources, groups and versions

The Kubernetes API is a REST API over HTTPS. Each kind of object lives at a predictable path:

/api/v1/namespaces/{ns}/pods/{name}                     # core group (no group name)
/apis/apps/v1/namespaces/{ns}/deployments/{name}        # group "apps", version "v1"
/apis/networking.k8s.io/v1/namespaces/{ns}/ingresses    # group "networking.k8s.io"
/api/v1/nodes/{name}                                    # cluster-scoped: no namespace

Three terms come up constantly. A group (apps, batch, networking.k8s.io) bundles related types. A version (v1alpha1, v1beta1, v1) signals stability: alpha can vanish without notice, beta is on by default only for some features, v1 is stable. A kind is the type name inside the object (Deployment); the resource is the lowercase plural used in URLs (deployments). Client libraries talk about GVK (group/version/kind) and GVR (group/version/resource) for exactly this reason.

The verbs are get, list, watch, create, update (full replace), patch, delete and deletecollection. RBAC rules are written in these verbs, so it pays to know them.

Some resources have subresources, separate endpoints with their own permissions: pods/log, pods/exec, pods/portforward, pods/eviction, deployments/scale, and /status on most types. Giving someone get pods does not let them read logs; that needs get pods/log.

kubectl api-resources                    # every type the server knows, with short names and scope
kubectl api-resources --namespaced=false # cluster-scoped types
kubectl api-versions                     # every group/version served
kubectl explain deployment.spec.strategy # field docs straight from the server's schema
kubectl explain pod.spec --recursive | less

kubectl explain is the most underused command in Kubernetes. It reads the schema from your actual cluster, including custom resources, so it is always the right version.

Anatomy of an object

Every object has the same top-level shape. Here is a Deployment as stored by the server, trimmed:

apiVersion: apps/v1              # group/version
kind: Deployment
metadata:
  name: checkout
  namespace: shop
  uid: 6c1d2b9e-…                # unique forever; a recreated object gets a new uid
  resourceVersion: "4810233"     # changes on every write; used for concurrency control
  generation: 7                  # increments only when spec changes
  creationTimestamp: "2026-10-02T09:14:11Z"
  labels:                        # identifying, queryable
    app.kubernetes.io/name: checkout
    app.kubernetes.io/part-of: shop
  annotations:                   # non-identifying metadata for tools and humans
    deployment.kubernetes.io/revision: "7"
  ownerReferences: []            # who owns me (pods are owned by ReplicaSets)
  finalizers: []                 # what must happen before I can be deleted
  managedFields: […]             # which client set which field (server-side apply)
spec:                            # desired state, written by you
  replicas: 3
  selector:
    matchLabels:
      app.kubernetes.io/name: checkout
  template: {…}
status:                          # observed state, written by controllers
  observedGeneration: 7
  replicas: 3
  readyReplicas: 2
  availableReplicas: 2
  conditions:
    - type: Available
      status: "False"
      reason: MinimumReplicasUnavailable

spec and status

spec is yours: the desired state. status belongs to the controllers: the observed state. They are written through different endpoints (status is a subresource), so a controller updating status never clobbers your spec and vice versa. When you debug, the question is almost always “why does status not match spec yet?”

generation and observedGeneration

metadata.generation increments whenever the spec changes. A well-behaved controller copies the generation it last acted on into status.observedGeneration. If observedGeneration < generation, the controller has not processed your latest change yet, so the rest of the status describes the previous spec. kubectl rollout status checks exactly this before it trusts the replica counts. Any controller you write should do the same.

resourceVersion

An opaque string that changes on every write to the object (it is derived from etcd’s revision counter). It does two jobs. It lets watches resume from a point in time (chapter 20), and it gives optimistic concurrency: an update that carries a stale resourceVersion is rejected with 409 Conflict instead of silently overwriting someone else’s change. Clients are expected to re-read and retry. Never parse it or compare it numerically.

Labels, selectors and annotations

Labels are short key/value pairs used to identify and group objects. They are how loosely coupled objects find each other: a Service does not list its pods, it has a selector and matches whatever pods carry those labels right now. ReplicaSets, NetworkPolicies, PodDisruptionBudgets, topology spread rules and anti-affinity all work the same way.

kubectl get pods -l app.kubernetes.io/name=checkout              # equality
kubectl get pods -l 'environment in (staging,prod),tier!=cache'  # set-based
kubectl get pods -l '!canary'                                    # label absent
kubectl get pods -L app.kubernetes.io/version                    # show a label as a column

Use the recommended labels (app.kubernetes.io/name, /instance, /version, /component, /part-of, /managed-by). Tools and dashboards understand them, and consistent labels are what make large clusters searchable.

Annotations are for everything else: build info, tool configuration, long strings. They are not indexed or selectable. If you would never query by it, it is an annotation.

Pitfall

A Deployment’s spec.selector is immutable after creation, and it must match the pod template’s labels. If you change pod labels in a way that no longer matches the selector, the API rejects it. If two Deployments have overlapping selectors in the same namespace, their ReplicaSets will fight over pods. Keep selectors narrow and stable; put changing things like versions in labels the selector does not use.

Namespaces and scope

A namespace is a scope for names: two Deployments called api can exist in team-a and team-b. It is also the unit most policy attaches to: RBAC RoleBindings, ResourceQuotas, LimitRanges, NetworkPolicies and Pod Security labels are all per-namespace. It is not a network or security boundary by itself. Pods in different namespaces can talk to each other freely unless a NetworkPolicy says otherwise.

Some resources are cluster-scoped and live outside any namespace: Nodes, PersistentVolumes, StorageClasses, ClusterRoles, CustomResourceDefinitions, IngressClasses, and Namespaces themselves.

Ownership and garbage collection

When the Deployment controller creates a ReplicaSet, it sets an ownerReference on the ReplicaSet pointing to the Deployment. The ReplicaSet does the same for its pods. That chain is how the garbage collector knows what to delete when you delete the top object.

  • Background cascading (the default): the owner is deleted at once, then the GC deletes dependents.
  • Foreground: the owner gets a deletionTimestamp and stays visible until all dependents with blockOwnerDeletion are gone.
  • Orphan: the owner is deleted and dependents are left behind with their owner reference removed. kubectl delete deploy x --cascade=orphan leaves the pods running, which is useful when migrating a workload to a different controller.

Owner references only work within the same namespace (or from namespaced to cluster-scoped owners). That is why a Helm release cannot “own” objects in another namespace through this mechanism.

Finalizers and deletion

Deletion is a two-phase process. When you delete an object that has finalizers (strings in metadata.finalizers), the API server does not remove it. It sets metadata.deletionTimestamp and leaves it. Each controller that added a finalizer is expected to notice, do its cleanup (delete a cloud load balancer, detach a disk, remove a DNS record), and then remove its own finalizer. When the list is empty, the object is actually deleted.

This is the reason for objects stuck in Terminating. A namespace stuck terminating is waiting for every object inside it to go, and one of those is usually waiting on a finalizer whose controller has been uninstalled. Removing a finalizer by hand (kubectl patch … --type=merge -p '{"metadata":{"finalizers":null}}') unblocks it, but it skips the cleanup that finalizer was protecting, so you might leak a cloud resource. Find out which controller owns it first.

How apply actually works

kubectl apply is not “create or replace.” It is a merge that tries to change only the fields you manage and leave other people’s fields alone.

Client-side apply (the old default) stores your last applied manifest in the annotation kubectl.kubernetes.io/last-applied-configuration. On the next apply it does a three-way diff between that annotation, your new file and the live object. If you remove a field from your file, it removes it from the live object; fields you never set (like a replica count changed by an autoscaler) are left alone.

Server-side apply (kubectl apply --server-side, and what controllers and GitOps tools increasingly use) moves this logic into the API server. Every field is owned by a field manager, recorded in managedFields. If you apply a value for a field another manager owns, you get a conflict instead of a silent overwrite, and you can choose to take ownership with --force-conflicts. This makes it explicit when, say, your CI pipeline and the HPA both think they own spec.replicas.

CommandSemanticsUse it for
kubectl createCreate; fails if it existsOne-off objects, scaffolding with --dry-run=client -o yaml
kubectl applyDeclarative merge of the fields you manageEverything you keep in Git
kubectl replaceFull PUT of the object; needs current resourceVersionRare; when you really want to drop all other fields
kubectl patchPartial change (strategic, merge or JSON patch)Scripts and surgical fixes
kubectl editGET, open editor, PUTExploration. Changes made this way drift from Git.

Pods in depth

The pod is the smallest thing Kubernetes schedules. Its lifecycle, its probes and its shutdown sequence decide whether your deploys are invisible to users or cause a burst of 502s every time.

Why pods and not containers

A pod is a group of containers that are always scheduled together on one node and share a network namespace and, optionally, volumes. They see each other on localhost and share one IP and one port space. Most pods have one main container. Additional containers exist to help it: a proxy, a log shipper, a config reloader.

Pods are mortal and disposable. A pod is never moved; if its node dies, the pod is gone and a controller creates a new pod, with a new name and a new IP, somewhere else. That is why you almost never create pods directly. You create a controller (Deployment, StatefulSet, Job) that creates pods for you and replaces them.

Phase, conditions and container states

A pod’s status.phase is deliberately coarse:

PhaseMeaning
PendingAccepted, but not all containers are running: waiting to be scheduled, pulling images, or running init containers
RunningBound to a node, and at least one container is running or restarting
SucceededAll containers exited 0 and will not restart (Jobs)
FailedAll containers have terminated and at least one failed, and they will not restart
UnknownThe node stopped reporting

The detail lives in conditions (PodScheduled, PodReadyToStartContainers, Initialized, ContainersReady, Ready) and in each container’s state: Waiting with a reason, Running, or Terminated with a reason and exit code. Each container also has a lastState, which is where you find why the previous instance died.

The STATUS column in kubectl get pods (and in k9s) is not the phase. It is a summary kubectl computes from these fields: it shows the most interesting container reason, such as CrashLoopBackOff, ImagePullBackOff, OOMKilled, Init:0/2 or Terminating. A pod can show CrashLoopBackOff while its phase is Running.

Restarts and CrashLoopBackOff

restartPolicy applies to all containers in the pod: Always (the default, and the only option for Deployments), OnFailure or Never (for Jobs). A restart happens in place: same pod, same node, same IP, new container. The restart counter goes up.

If a container keeps exiting, the kubelet waits longer between restarts: starting at 10 seconds and doubling up to five minutes. While it waits, the container is Waiting with reason CrashLoopBackOff. That reason is not an error in itself; it only means “this keeps dying and I am pausing before trying again.” The actual cause is in the previous container’s logs and exit code:

kubectl logs checkout-7d9f8-x2x4q --previous
kubectl get pod checkout-7d9f8-x2x4q -o jsonpath='{.status.containerStatuses[0].lastState}'

Init containers and sidecars

Init containers run one after another, each to completion, before the app containers start. If one fails, the kubelet retries it according to the restart policy, and the pod stays at Init:N/M. Use them for work that must finish first: rendering a config file into a shared emptyDir, waiting for a dependency’s DNS name to resolve, fixing volume permissions.

Sidecars are helper containers that run alongside the app for its whole life. For years they were just ordinary extra containers, which caused two problems: no ordering guarantee (the app might start before its proxy was ready) and Jobs that never finished (the job’s main container exited but the sidecar kept running). Kubernetes now has native sidecars, stable since v1.33: an init container with restartPolicy: Always. It starts in init order, the next containers wait for it to be started (and ready, if it has a startup or readiness probe), it keeps running alongside the app, and it is stopped after the app containers during shutdown. A Job completes when its regular containers finish.

spec:
  initContainers:
    - name: proxy                 # native sidecar
      image: envoyproxy/envoy:v1.31.0
      restartPolicy: Always
      readinessProbe:
        httpGet: { path: /ready, port: 9901 }
  containers:
    - name: app
      image: registry.example.com/checkout:2026-11-20-a41c9e2

Probes, properly

The kubelet runs three kinds of probe, and they have very different consequences. Confusing them is the most common way well-meaning teams make outages worse.

ProbeQuestion it answersOn failure
startupHas the app finished starting?Keeps waiting until failureThreshold × periodSeconds, then restarts the container. Other probes are disabled until it succeeds.
readinessShould this instance receive traffic right now?Pod is marked not ready and removed from Service endpoints. No restart.
livenessIs the process stuck beyond recovery?Container is killed and restarted.

Each probe can be httpGet (2xx or 3xx is success), tcpSocket, grpc or exec. Timing fields: initialDelaySeconds, periodSeconds (default 10), timeoutSeconds (default 1), failureThreshold (default 3), successThreshold.

containers:
  - name: app
    startupProbe:                 # allow up to 5 minutes for a slow cold start
      httpGet: { path: /healthz, port: http }
      periodSeconds: 5
      failureThreshold: 60
    readinessProbe:               # can I serve? may check that critical deps are reachable
      httpGet: { path: /ready, port: http }
      periodSeconds: 5
      failureThreshold: 2
    livenessProbe:                # am I wedged? checks only this process
      httpGet: { path: /healthz, port: http }
      periodSeconds: 10
      timeoutSeconds: 3
      failureThreshold: 3

Pitfall: liveness probes that check dependencies

If your liveness endpoint checks the database and the database has a hiccup, every replica fails liveness at the same moment and Kubernetes restarts all of them together. Your service goes from degraded to fully down, then all instances reconnect at once when they come back. Liveness should only detect states the process cannot recover from by itself, such as a deadlock. Dependency checks belong in readiness, if anywhere. Many services are better off with no liveness probe at all than with a careless one.

Other common mistakes: a 1-second timeout on a JVM or Python service that occasionally pauses for garbage collection; using the same endpoint and thresholds for readiness and liveness, so a slow instance is killed instead of rested; and no readiness probe at all, so a pod gets traffic the moment its process starts, before it has warmed caches or opened connections.

The shutdown sequence

This is where most “we get errors during every deploy” problems come from. When a pod is deleted, for a rollout, a scale-down or a node drain, two things start at the same time and nothing coordinates them:

  1. The API server sets deletionTimestamp and a grace period (terminationGracePeriodSeconds, default 30).
  2. Path A, on the node: the kubelet runs each container’s preStop hook, if any, then sends SIGTERM to PID 1. If the container is still running when the grace period ends, it gets SIGKILL.
  3. Path B, across the cluster: the EndpointSlice controller marks the pod as terminating and not ready, kube-proxy on every node rewrites its rules, ingress controllers and service meshes update their upstream lists, and cloud load balancers deregister the target. This takes anywhere from milliseconds to several seconds.

If path A wins the race (the app gets SIGTERM and exits immediately) while path B is still propagating, some nodes keep sending new connections to a process that has stopped listening. Users see connection resets and 502s.

The standard fix has two parts. First, a short preStop sleep, so the process keeps serving normally while removal propagates. Second, the application handles SIGTERM by stopping accepting new connections, finishing in-flight requests, closing keep-alive connections, and exiting.

spec:
  terminationGracePeriodSeconds: 45     # preStop + drain time must fit inside this
  containers:
    - name: app
      lifecycle:
        preStop:
          sleep:
            seconds: 5                  # built-in sleep action; older clusters use exec: ["sleep","5"]

Mental model

The pod finds out it is dying before the rest of the cluster stops sending it traffic. Your job is to keep serving until the cluster has caught up, then leave cleanly.

Debugging inside a pod

Production images are often distroless: no shell, no curl. Ephemeral containers let you attach a temporary debug container to a running pod, sharing its network namespace and, with --target, its process namespace:

kubectl debug -it checkout-7d9f8-x2x4q --image=nicolaka/netshoot --target=app
# now: ss -tlnp, curl localhost:8080/ready, dig, tcpdump, ps aux (sees app's processes)

Ephemeral containers cannot be removed once added, and they have no resource guarantees. They are for investigation, not for running things.

Deployments and other controllers

You rarely manage pods. You manage controllers that manage pods, and each controller makes a different promise about identity, ordering and completion. Picking the right one is a design decision.

ReplicaSet: the counting loop

A ReplicaSet has three things: a replica count, a label selector, and a pod template. Its controller counts live pods matching the selector and creates or deletes pods to reach the count. That is the whole job. It does not know about versions or rollouts. If you change a ReplicaSet’s template, existing pods are not touched; only pods created afterwards use the new template.

You almost never create ReplicaSets yourself. Deployments create them.

Deployment: rollouts on top of ReplicaSets

A Deployment adds versioning. When you change its pod template, the Deployment controller computes a hash of the template, creates a new ReplicaSet named <deployment>-<hash>, and then shifts replicas from the old ReplicaSet to the new one in steps. Each pod gets a pod-template-hash label so the two ReplicaSets’ selectors never overlap.

Old ReplicaSets are kept, scaled to zero, as revision history (revisionHistoryLimit, default 10). A rollback is nothing special: it copies an old ReplicaSet’s template back into the Deployment, which triggers a normal rollout in the other direction.

kubectl rollout status deploy/checkout          # blocks until done or failed
kubectl rollout history deploy/checkout
kubectl rollout history deploy/checkout --revision=6
kubectl rollout undo deploy/checkout            # back to the previous revision
kubectl rollout undo deploy/checkout --to-revision=4
kubectl rollout restart deploy/checkout         # new pods, same spec (stamps an annotation on the template)
kubectl rollout pause deploy/checkout           # batch several edits into one rollout
kubectl rollout resume deploy/checkout

Strategy parameters

The RollingUpdate strategy (the default) is controlled by two numbers:

  • maxSurge: how many pods above the desired count may exist during the rollout. Default 25%, rounded up.
  • maxUnavailable: how many pods below the desired count may be unavailable. Default 25%, rounded down. Both cannot be zero.

For a latency-sensitive service with spare capacity, maxUnavailable: 0, maxSurge: 1 (or 25%) is the usual choice: never drop below full capacity, add new pods first. For a large deployment where you are short on capacity, allowing some unavailability makes the rollout possible at all. The Recreate strategy kills all old pods before starting new ones. It causes downtime, but it is the right choice when two versions must never run at once, or when a ReadWriteOnce volume cannot be attached to two pods.

Three more fields shape a rollout. minReadySeconds makes a new pod count as available only after it has been ready for that long, which catches pods that pass readiness and then crash. progressDeadlineSeconds (default 600) is how long the rollout may go without progress before the Deployment’s Progressing condition turns false with reason ProgressDeadlineExceeded. Note that Kubernetes does not roll back automatically when this happens. It just reports the failure; your pipeline or a progressive delivery tool has to act on it.

Pitfall: config changes do not roll pods

A Deployment rolls out only when its pod template changes. Editing a ConfigMap that pods read through environment variables changes nothing until pods restart. The common fixes are a checksum of the config in a template annotation (Helm’s standard trick), a ConfigMap with a content hash in its name (Kustomize’s generator), or kubectl rollout restart.

StatefulSet: identity and order

Deployment pods are interchangeable cattle with random names. Some software needs pets: a database replica must know it is replica 0, keep the same disk across restarts, and be reachable at a predictable address. A StatefulSet provides:

  • Stable names. Pods are db-0, db-1, db-2. If db-1 is deleted, the replacement is also db-1.
  • Stable network identity. With a headless Service (clusterIP: None) named in serviceName, each pod gets a DNS name: db-1.db.shop.svc.cluster.local.
  • Stable storage. volumeClaimTemplates create one PersistentVolumeClaim per pod (data-db-1), and the replacement db-1 reattaches the same claim.
  • Ordering. With the default podManagementPolicy: OrderedReady, pods are created 0, 1, 2, each waiting for the previous to be ready, and removed in reverse. Parallel drops the ordering when you only need identity.

Rolling updates go from the highest ordinal down, one pod at a time. The partition field lets you stage them: with partition: 2, only pods with ordinal ≥ 2 are updated, so you can canary one replica of a database before the rest.

Pitfall

A StatefulSet gives a database identity and storage. It does not make it a cluster. Replication, leader election, failover and backups are still the database’s job, which is why serious stateful workloads run under an operator (chapter 21). Also: scaling a StatefulSet down does not delete its PVCs by default, and with OrderedReady, a pod that never becomes ready blocks the rollout until you fix or delete it by hand.

DaemonSet: one per node

A DaemonSet runs one pod on every node, or every node matching a selector. New nodes get a pod automatically. This is how node-level agents run: CNI plugins, kube-proxy, log shippers, node exporters, CSI node drivers, security agents. DaemonSet pods usually need tolerations to run on tainted nodes (control-plane nodes, GPU pools). They roll out with maxUnavailable per node, and since the pods are tied to nodes, maxSurge is only useful when two copies can share a host safely.

Jobs and CronJobs: run to completion

A Job runs pods until a number of them succeed. Its main fields:

  • completions and parallelism: how many successful pods are needed, and how many may run at once.
  • completionMode: Indexed: each pod gets an index (JOB_COMPLETION_INDEX), which makes static work splitting easy.
  • backoffLimit (default 6): how many failures before the Job is marked failed. podFailurePolicy lets you fail fast on specific exit codes and ignore disruptions.
  • activeDeadlineSeconds: a hard time limit for the whole Job.
  • ttlSecondsAfterFinished: delete the Job and its pods after it finishes, so they do not pile up.

A CronJob creates Jobs on a cron schedule (timeZone is supported). concurrencyPolicy decides what happens if the previous run is still going: Allow (default), Forbid (skip) or Replace. startingDeadlineSeconds bounds how late a missed run may start.

In production

Treat every Job as “at least once, maybe never.” A pod can be retried after doing half its work, a node failure can rerun a step that already succeeded, and a CronJob can miss a slot if the controller is down at the wrong time. Make job logic idempotent: use upserts, unique keys, and checkpoints, never “increment a counter” without a guard.

Requests, limits and QoS

Requests decide where a pod goes. Limits decide what happens when it gets greedy. The two behave differently for CPU and memory, and that difference explains most latency spikes and mysterious restarts.

Two numbers, two jobs

resources:
  requests:
    cpu: 500m        # half a core
    memory: 512Mi
  limits:
    cpu: "1"
    memory: 512Mi

Requests are a reservation used at scheduling time. The scheduler only places a pod on a node where the sum of requests of all pods, plus this one, fits within the node’s allocatable capacity. Actual usage does not matter to the scheduler. A node can be at 5% real CPU and still refuse new pods because it is fully requested.

Limits are enforced by the kernel at runtime through cgroups, and the enforcement is very different for the two resources:

CPU (compressible)Memory (incompressible)
Request becomescpu.weight: a relative share when the CPU is contendedUsed for scheduling and eviction ranking only
Limit becomescpu.max: a quota per 100ms periodmemory.max: a hard ceiling
Exceeding the limitThe container is throttled: paused until the next periodThe container is OOM-killed: exit 137, reason OOMKilled
Visible asLatency, not errorsRestarts

Units: CPU in cores or millicores (250m = 0.25 core). Memory in bytes with binary suffixes (Mi, Gi) or decimal ones (M, G). 512M is about 488Mi. Beware the classic typo memory: 512m, which means 0.512 bytes.

CPU throttling, the quiet latency killer

The CFS quota works in 100ms periods. A limit of 1 CPU means “100ms of CPU time per 100ms of wall time,” summed across all threads. A service with eight busy threads can spend that budget in 12.5ms, then sit frozen for the remaining 87.5ms of the period. Average CPU usage in your dashboard reads 30%, yet tail latency has periodic 80ms stalls.

The evidence is in cgroup counters: nr_throttled and throttled_usec in cpu.stat, exposed by cAdvisor as container_cpu_cfs_throttled_periods_total and container_cpu_cfs_periods_total. A throttled-period ratio above a few percent on a latency-sensitive service is worth fixing.

In production: the CPU limits debate

A common position among experienced operators: always set CPU requests accurately, set memory requests equal to memory limits, and be cautious with CPU limits on latency-sensitive services, because requests already guarantee each pod its share under contention and limits only add throttling when spare CPU exists. The counter-arguments are real: in multi-tenant clusters, limits stop one team from soaking up idle CPU and then suffering when it disappears; they make performance predictable across environments; and some runtimes size thread pools from the limit. Whatever your organisation chooses, measure throttling, and make the choice deliberately.

Runtimes need to know their budget. The JVM is container-aware (use -XX:MaxRAMPercentage rather than a fixed -Xmx that can exceed the limit). Recent Go versions derive GOMAXPROCS from the CPU limit; older ones need automaxprocs. Node.js sizes its heap from available memory in newer versions but often still benefits from an explicit --max-old-space-size below the limit.

Memory: OOM kills versus evictions

Two different mechanisms remove memory-hungry containers, and you should be able to tell them apart from a describe.

An OOM kill is the kernel acting on one container that exceeded its own memory.max. The container is killed with SIGKILL, lastState.terminated.reason is OOMKilled, exit code 137, and the kubelet restarts it in place. The pod stays.

A node-pressure eviction is the kubelet acting because the node is running low on memory (or disk, or PIDs), regardless of individual limits. It chooses pods to remove, terminates them, and marks them Failed with reason Evicted. The pod is gone, and its controller creates a replacement elsewhere. Evictions mean your requests are too low relative to real usage, so the scheduler is over-packing nodes.

The memory figure that matters for both is the working set (container_memory_working_set_bytes), which roughly excludes reclaimable page cache. That is also what kubectl top shows.

QoS classes

From the requests and limits of all containers, Kubernetes assigns each pod a Quality of Service class. It decides eviction order and the kernel’s OOM score.

ClassRuleUnder node pressure
GuaranteedEvery container has CPU and memory requests equal to limitsLast to be evicted
BurstableAt least one request or limit set, but not GuaranteedEvicted in order of how far usage exceeds requests
BestEffortNo requests or limits at allFirst to go

Pods with no requests are dangerous beyond eviction: the scheduler thinks they cost nothing, so it can stack any number of them on a node. Every production workload should have requests.

Node allocatable

Not all of a node is for pods. Allocatable = capacity − kube-reserved (kubelet, runtime) − system-reserved (OS daemons) − the hard eviction threshold. kubectl describe node shows capacity, allocatable, and an “Allocated resources” table of requests and limits as a percentage of allocatable. Limits may sum to more than 100%; that overcommit is normal and is exactly why evictions exist.

Namespace guardrails

LimitRange sets per-container defaults, minimums and maximums in a namespace, so a pod that forgets requests still gets sensible ones. ResourceQuota caps the totals in a namespace: total CPU requests, memory limits, number of pods, Services, PVCs, LoadBalancers. Once a quota covers CPU or memory, every new pod in that namespace must declare those resources or be rejected, which is where LimitRange defaults come in handy.

Pitfall

When a quota or admission policy rejects a pod, the pod never exists, so kubectl get pods shows nothing wrong: there are just fewer pods than expected. The error is an event on the ReplicaSet, for example FailedCreate … exceeded quota. Run kubectl describe rs, or in k9s look at the ReplicaSet, when pods are missing rather than failing.

Recent Kubernetes versions also support in-place resize: changing a running container’s CPU and memory through the pod’s resize subresource without recreating it, subject to the container’s resizePolicy. It is useful for vertical autoscaling and for giving a slow-starting service extra CPU during startup.

Scheduling and disruption

Where a pod lands decides what can take it down. Spreading, pinning, repelling and protecting pods are the tools that turn three replicas into actual redundancy.

How the scheduler decides

The scheduler takes pods from a queue one at a time and runs them through a pipeline of plugins:

  1. Filter. Remove nodes that cannot run the pod: not enough allocatable CPU or memory for its requests, a nodeSelector or required affinity that does not match, a taint it does not tolerate, a host port already in use, a volume that cannot attach in that zone.
  2. Score. Rank the remaining nodes: spread pods of the same workload, balance resource usage, prefer nodes that already have the image, honour preferred affinities.
  3. Reserve and bind. Assume the pod is on the winner in its cache, then asynchronously write the Binding.

When no node survives filtering, the pod stays Pending with a FailedScheduling event that tallies the reasons:

0/6 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: },
2 Insufficient memory, 3 node(s) didn't match pod anti-affinity rules.
preemption: 0/6 nodes are available: 6 No preemption victims found for incoming pod.

Read it as a census: each node is counted under the first filter that rejected it. This message tells you that the fix is either more memory or fewer anti-affinity constraints, not more nodes in general.

Attracting pods to nodes

nodeSelector is the simple form: the node must have all these labels.

Node affinity is the expressive form. requiredDuringSchedulingIgnoredDuringExecution is a hard rule; preferredDuringSchedulingIgnoredDuringExecution adds weight to the score. The awkward suffix means what it says: the rule is only checked at scheduling time, and if a node’s labels change later, running pods stay put.

affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: kubernetes.io/arch
              operator: In
              values: [arm64]
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 50
        preference:
          matchExpressions:
            - key: node.kubernetes.io/instance-type
              operator: In
              values: [m7g.xlarge]

Repelling pods: taints and tolerations

A taint on a node repels pods that do not tolerate it. Effects: NoSchedule (new pods without a toleration are not placed), PreferNoSchedule (avoid if possible), and NoExecute (also evicts running pods that do not tolerate it, optionally after tolerationSeconds).

kubectl taint nodes gpu-1 nvidia.com/gpu=present:NoSchedule
kubectl taint nodes gpu-1 nvidia.com/gpu=present:NoSchedule-     # trailing dash removes it
tolerations:
  - key: nvidia.com/gpu
    operator: Exists
    effect: NoSchedule

A toleration permits; it does not attract. To make a pool dedicated, combine a taint (keep others out) with node affinity on the workload (make it go there).

Kubernetes uses taints itself. When a node stops heartbeating, the node lifecycle controller adds node.kubernetes.io/unreachable:NoExecute (or not-ready). Every pod gets default tolerations for these with tolerationSeconds: 300, which is why pods on a dead node are only replaced about five minutes after the node disappears. Latency-critical stateless services sometimes lower this; doing so trades faster failover against more churn during brief network blips.

Spreading pods out

Three replicas on one node is one replica with extra steps. Use topology spread constraints to spread across nodes and zones:

topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels: { app.kubernetes.io/name: checkout }
    matchLabelKeys: [pod-template-hash]    # spread each rollout's pods independently
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: ScheduleAnyway
    labelSelector:
      matchLabels: { app.kubernetes.io/name: checkout }

maxSkew is the largest allowed difference in matching pod counts between any two domains. DoNotSchedule is a hard rule; ScheduleAnyway only affects scoring. Like affinity, constraints are evaluated at scheduling time. After node replacements or scale-downs the spread can drift, and nothing rebalances it unless you run the descheduler.

Pod anti-affinity (“do not put me next to pods with label X in the same topology domain”) does a similar job and is still common, but required anti-affinity across hostnames effectively caps replicas at the node count and is expensive to compute in big clusters. Prefer topology spread for availability; keep pod affinity for co-location needs such as “run next to the cache.”

Priority and preemption

A PriorityClass gives pods a numeric priority. When a high-priority pod cannot be scheduled, the scheduler may preempt: evict lower-priority pods to make room. Built-in classes system-cluster-critical and system-node-critical protect core add-ons like CoreDNS. A sensible platform has a few classes, for example critical services, default, and preemptible batch, so a flood of batch jobs can never starve the checkout service. A class with preemptionPolicy: Never jumps the queue without evicting anyone.

Voluntary disruptions and PodDisruptionBudgets

Pods disappear for two kinds of reasons. Involuntary: hardware failure, kernel panic, node-pressure eviction, a cloud VM being reclaimed. Voluntary: someone draining a node for an upgrade, the cluster autoscaler removing an underused node. Voluntary disruptions go through the Eviction API, and the Eviction API respects PodDisruptionBudgets.

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: checkout }
spec:
  maxUnavailable: 1          # or minAvailable: 2
  selector:
    matchLabels: { app.kubernetes.io/name: checkout }

During kubectl drain, an eviction that would take the workload below its budget is refused with a 429, and drain retries until it can proceed. This is how a cluster upgrade can walk across every node without ever taking your service below capacity.

Pitfall: budgets that can never be satisfied

A PDB with minAvailable: 1 on a single-replica Deployment, or maxUnavailable: 0 on anything, blocks every drain forever. Node upgrades stall, autoscalers cannot remove nodes, and someone eventually force-deletes pods at 2 a.m. A PDB must always allow at least one disruption when the workload is healthy. Also remember what PDBs do not cover: node crashes, and a Deployment’s own rolling update, which follows maxUnavailable instead.

kubectl cordon node-3          # mark unschedulable; running pods stay
kubectl drain node-3 --ignore-daemonsets --delete-emptydir-data   # evict everything that can be evicted
kubectl uncordon node-3

Pod networking and Services

Kubernetes networking has a few simple rules and an implementation that is mostly Linux plumbing. Once you can trace a packet from one pod to another through a Service, network bugs stop being mysterious.

The model

Kubernetes sets three requirements and leaves the implementation to a plugin:

  1. Every pod gets its own IP address.
  2. Pods can reach every other pod by that IP, on any node, without NAT.
  3. Agents on a node (such as the kubelet) can reach all pods on that node.

The result is a flat network that looks like every pod is a small VM on one big LAN. Ports never collide between pods, because each pod has its own network namespace and IP.

How a pod gets on the network

When the runtime creates a pod sandbox, it calls the CNI (Container Network Interface) plugin with an ADD command. A typical plugin then:

  1. creates a veth pair, a virtual cable with two ends;
  2. moves one end into the pod’s network namespace and names it eth0;
  3. attaches the other end to the host, either to a bridge or as a routed interface;
  4. allocates an IP from the node’s pod CIDR (IPAM) and sets the pod’s default route.

Traffic between pods on the same node goes pod → veth → host → veth → pod. Traffic to another node depends on the plugin’s strategy:

StrategyHow cross-node packets travelExamples
OverlayEncapsulated in VXLAN or Geneve between node IPs; the underlying network never sees pod IPsFlannel, Calico VXLAN mode, Cilium tunnel mode
Native routingPod CIDRs are routed directly, via BGP or cloud route tablesCalico BGP, Cilium native routing
Cloud VPC IPsPods get real VPC addresses on the node’s network interfacesAWS VPC CNI, Azure CNI

Overlays work anywhere but add encapsulation overhead and reduce the MTU. VPC-native networking is fast and makes pods first-class on the cloud network, but each node can hold only as many pod IPs as its interfaces allow, which can cap pod density well below what CPU and memory would allow.

Services: a stable name for moving targets

Pod IPs change every time a pod is replaced. A Service gives a set of pods, chosen by a label selector, one stable virtual IP (the ClusterIP) and one DNS name.

apiVersion: v1
kind: Service
metadata: { name: checkout, namespace: shop }
spec:
  selector: { app.kubernetes.io/name: checkout }
  ports:
    - name: http
      port: 80            # what clients connect to
      targetPort: http    # the container port, by name or number

The ClusterIP is not a real address

No interface owns 10.96.14.2, and you cannot ping it in most setups. kube-proxy on every node watches Services and EndpointSlices and writes rules that rewrite packets addressed to the virtual IP. In the classic iptables mode, a chain per Service picks one endpoint at random with probability rules and applies DNAT to that pod’s IP and port. The newer nftables mode does the same with better performance at scale, IPVS mode uses the kernel’s load balancer, and eBPF dataplanes like Cilium replace kube-proxy and do the translation at the socket or interface level.

EndpointSlices are written by the EndpointSlice controller: for each Service with a selector, it lists matching pods and records their IPs, ports, and conditions (ready, serving, terminating). Only ready endpoints get traffic. This is the link between a readiness probe failing on one node and traffic stopping on every other node. (The older Endpoints API still exists but is deprecated; EndpointSlices are the source of truth.)

Pitfall: load balancing is per connection

kube-proxy picks a backend when a connection is opened, not per request. HTTP/1.1 keep-alive, HTTP/2 and gRPC hold one long connection and send everything down it, so a client with one connection talks to one pod forever. After a scale-up, new pods sit idle while old ones are overloaded. Fixes: client-side load balancing over a headless Service, a proxy or service mesh that balances per request, or periodically recycling connections (for example, a max connection age on the server).

Service types

TypeWhat you get
ClusterIPA virtual IP reachable inside the cluster. The default.
NodePortClusterIP, plus a port in 30000–32767 opened on every node that forwards to the Service.
LoadBalancerNodePort plus an external load balancer provisioned by the cloud controller (or MetalLB and similar on bare metal).
ExternalNameOnly a DNS CNAME to an outside name. No proxying.
Headless (clusterIP: None)No virtual IP. DNS returns the ready pod IPs directly. Used by StatefulSets and client-side load balancing.

For traffic from outside, externalTrafficPolicy: Cluster (the default) lets any node accept traffic and forward it to a pod anywhere, at the cost of an extra hop and source NAT that hides the client IP. Local keeps the client IP and avoids the hop, but only nodes with a local ready pod will pass health checks, and load can be uneven if pods are not spread evenly.

DNS

CoreDNS runs as a Deployment in kube-system behind a Service, and every pod’s /etc/resolv.conf points at it. Records:

checkout.shop.svc.cluster.local      A     → ClusterIP (or pod IPs if headless)
db-0.db.shop.svc.cluster.local       A     → that StatefulSet pod's IP
_http._tcp.checkout.shop.svc.cluster.local   SRV  → port and target names

A pod in shop gets this resolv.conf:

nameserver 10.96.0.10
search shop.svc.cluster.local svc.cluster.local cluster.local
options ndots:5

The search list is why curl checkout works within a namespace and curl checkout.shop works across namespaces. The ndots:5 option has a cost: any name with fewer than five dots is tried with each search suffix before being tried as-is. A call to api.stripe.com first queries api.stripe.com.shop.svc.cluster.local, then the other suffixes, each for A and AAAA records, before the real lookup. Services that call external APIs heavily generate several times the DNS traffic they need.

In production

Fixes, from simplest: write external names with a trailing dot (api.stripe.com.) so they are treated as absolute; lower ndots for a workload via dnsConfig.options; run NodeLocal DNSCache so lookups hit a cache on the node. When you see intermittent 5-second delays, suspect DNS first: that is the default resolver retry timeout.

Ingress, Gateway API, NetworkPolicy

Services handle traffic inside the cluster. This chapter covers how HTTP traffic gets in from outside, how the APIs for that are changing, and how to stop traffic you do not want.

North-south and east-west

Traffic entering or leaving the cluster is north-south. Traffic between workloads inside it is east-west. A LoadBalancer Service per application handles north-south at layer 4, but it gives you one cloud load balancer (and one bill) per Service and no HTTP features. For HTTP you want one shared layer-7 entry point that routes by host and path, terminates TLS, and forwards to Services.

Ingress, and why it is being left behind

The Ingress resource was the original answer: rules mapping hosts and paths to Services, implemented by an ingress controller (a proxy such as NGINX, HAProxy, Traefik or a cloud load balancer integration) selected through an IngressClass.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: shop }
spec:
  ingressClassName: example
  tls:
    - hosts: [shop.example.com]
      secretName: shop-tls
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend: { service: { name: checkout, port: { name: http } } }

Ingress covers only the basics. Anything beyond host and path matching (timeouts, rewrites, canary weights, header matching, rate limits) was added through controller-specific annotations, so an Ingress written for one controller rarely worked on another. The Ingress API is now frozen: it still works and is not being removed, but it gets no new features.

In November 2025, Kubernetes SIG Network announced the retirement of the community ingress-nginx controller, one of the most widely deployed controllers, with maintenance ending in March 2026. Existing installations keep running, but they no longer get fixes or security patches. If your company still runs it, migrating is a real piece of senior-level work: inventory every Ingress and its annotations, choose a replacement, and move services one at a time. SIG Network’s ingress2gateway tool converts many common annotations.

Gateway API

Gateway API is the successor. It splits the job into resources owned by different roles:

ResourceOwned byDescribes
GatewayClassInfrastructure providerWhich implementation handles gateways of this class (Envoy Gateway, Cilium, Istio, a cloud LB, …)
GatewayPlatform teamAn actual entry point: listeners, ports, hostnames, TLS certificates, and which namespaces may attach routes
HTTPRoute, GRPCRoute, …Application teamsMatching rules and backends, attached to a Gateway through parentRefs
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata: { name: public, namespace: infra }
spec:
  gatewayClassName: example
  listeners:
    - name: https
      protocol: HTTPS
      port: 443
      hostname: "*.example.com"
      tls:
        certificateRefs: [{ name: wildcard-tls }]
      allowedRoutes:
        namespaces: { from: All }
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: checkout, namespace: shop }
spec:
  parentRefs: [{ name: public, namespace: infra }]
  hostnames: [shop.example.com]
  rules:
    - matches: [{ path: { type: PathPrefix, value: /api } }]
      backendRefs:
        - { name: checkout,        port: 80, weight: 90 }
        - { name: checkout-canary, port: 80, weight: 10 }

Traffic splitting, header and query matching, redirects, rewrites, header modification, timeouts and request mirroring are part of the spec, so routes are portable between implementations. Cross-namespace references to backends need an explicit ReferenceGrant in the target namespace, which keeps one team from routing traffic to another team’s Services without permission.

Certificates

TLS certificates live in Secrets of type kubernetes.io/tls. In practice cert-manager issues and renews them: you declare a Certificate (or annotate a Gateway), it solves an ACME challenge or asks your internal CA, and keeps the Secret fresh. Expired certificates remain one of the most common avoidable outages, so alert on certificate expiry even with automation in place.

NetworkPolicy: a firewall for pods

By default every pod can talk to every other pod in every namespace. NetworkPolicy restricts that. The rules are subtle enough that most people get them wrong at least once:

  • A policy selects pods with podSelector and lists allowed ingress and/or egress traffic.
  • Pods not selected by any policy remain fully open.
  • Once a pod is selected by any policy that covers a direction (its policyTypes), only traffic explicitly allowed by some policy is permitted in that direction. Policies are additive allow-lists; core NetworkPolicy has no deny rules.
  • Enforcement is done by the CNI plugin. If your plugin does not implement NetworkPolicy, the objects are accepted and silently do nothing.

The standard pattern is a default deny per namespace, then specific allows. Remember DNS: once egress is restricted, pods cannot resolve names unless you allow traffic to CoreDNS.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny, namespace: shop }
spec:
  podSelector: {}                 # every pod in the namespace
  policyTypes: [Ingress, Egress]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-dns, namespace: shop }
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
    - to:
        - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: kube-system } }
          podSelector: { matchLabels: { k8s-app: kube-dns } }
      ports:
        - { protocol: UDP, port: 53 }
        - { protocol: TCP, port: 53 }
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: checkout-from-gateway, namespace: shop }
spec:
  podSelector: { matchLabels: { app.kubernetes.io/name: checkout } }
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: infra } }
      ports: [{ port: 8080 }]

Pitfall: one dash changes the meaning

In a from list, a namespaceSelector and a podSelector in the same list item are ANDed: pods with that label, in namespaces with that label. Written as two list items, each starting with its own dash, they are ORed: any pod in those namespaces, or pods with that label in the policy’s own namespace. The second form is far more permissive and looks almost identical. The DNS policy above uses the AND form deliberately.

Also note that ports in a policy refers to the destination port on the pod (the container port), not the Service port.

Service meshes, briefly

A service mesh (Istio, Linkerd, Cilium’s mesh features) adds a layer-7 proxy to east-west traffic, either as a sidecar per pod or as shared node and waypoint proxies (Istio’s ambient mode). In return you get mutual TLS between workloads with workload identity, per-request load balancing (solving the long-lived connection problem from chapter 9), retries, timeouts, traffic splitting and uniform metrics. The cost is real: more moving parts, more latency, harder debugging, and upgrades that touch every workload. Adopt one when you need several of those features across many services, not for one of them.

ConfigMaps and Secrets

Configuration looks like the simplest part of Kubernetes. The interesting questions are when a change actually reaches a running process, and who can read your secrets without you noticing.

ConfigMaps

A ConfigMap holds non-secret configuration as key/value pairs (data for text, binaryData for bytes), up to about 1 MiB in total because it is stored as one etcd object. Images stay environment-agnostic; the environment-specific values live in the cluster.

kubectl create configmap checkout-config \
  --from-literal=LOG_LEVEL=info \
  --from-file=app.yaml=./config/prod.yaml \
  --dry-run=client -o yaml > checkout-config.yaml

Three ways to consume config, three update behaviours

How it is consumedWhen changes reach the process
Environment variables (env.valueFrom, envFrom)Never. Environment is fixed when the container starts. Only a restart picks up changes.
Volume mount of the whole ConfigMapEventually. The kubelet refreshes files on its sync loop, typically within a minute or so. The app must notice (watch the file or reload on a signal).
Volume mount with subPathNever. A subPath mount is a bind mount of one file at start time.

The kubelet updates mounted files atomically: the volume contains a timestamped directory and a ..data symlink, and an update writes a new directory and swaps the symlink. Apps that watch a file path with inotify must watch the directory or handle the symlink swap, or they miss updates.

Because environment-based config never updates, teams often want a Deployment to roll whenever its config changes. There are two clean ways. Name the ConfigMap after a hash of its content (Kustomize’s configMapGenerator does this), so a config change becomes a template change. Or put a checksum of the config in a pod template annotation (the Helm pattern). Both make config changes go through the same rollout, history and rollback as code changes.

Mark ConfigMaps and Secrets immutable: true when you use the hash-naming approach. The kubelet stops watching them, which reduces API server load in large clusters, and nobody can edit a live config in place.

Secrets: what they are and are not

A Secret is structurally almost identical to a ConfigMap. Its values are base64-encoded, which is an encoding for binary safety, not encryption. What Secrets do get:

  • A separate resource type, so RBAC can grant ConfigMap access without Secret access.
  • Mounting through tmpfs on the node, so they are not written to the node’s disk.
  • Delivery only to nodes that run a pod using them.
  • Optional encryption at rest in etcd, if the cluster administrator configures an EncryptionConfiguration, ideally with a KMS provider. Managed clusters usually offer this as a setting. Without it, anyone with a copy of etcd or its backups can read every Secret.

Typed Secrets add validation and conventions: kubernetes.io/tls (keys tls.crt, tls.key), kubernetes.io/dockerconfigjson (registry credentials for imagePullSecrets), and Opaque for everything else.

Pitfall: who can really read a Secret

RBAC get or list on Secrets in a namespace grants every Secret in it; list returns their contents too, not just names. Less obviously, anyone who can create pods in a namespace can mount any Secret in that namespace into a pod they control and print it. So can anyone who can create or edit Deployments, Jobs or CronJobs there. Treat “can deploy to namespace X” as “can read all of X’s Secrets,” and design namespaces with that in mind.

Keeping secrets out of Git and etcd

You cannot commit plain Secrets to a GitOps repository. The common approaches:

  • Encrypted in Git: Sealed Secrets (encrypt with a key only the in-cluster controller holds) or SOPS (encrypt values with KMS or age keys, decrypt during deploy).
  • Synced from a secret manager: External Secrets Operator reads from AWS Secrets Manager, GCP Secret Manager, Vault and others, and writes Kubernetes Secrets, refreshing them on a schedule.
  • Mounted directly: the Secrets Store CSI driver mounts secrets from the external store as files, optionally without creating Kubernetes Secrets at all.

Whichever you pick, rotation is the real test: can you change a database password without an outage? That needs the app to reload credentials, or a rolling restart, and usually a period where both old and new credentials are valid.

The Downward API

A pod can learn about itself without calling the API server. The Downward API exposes fields such as the pod name, namespace, node name, pod IP, labels, annotations and its own resource limits as environment variables or files:

env:
  - name: POD_NAME
    valueFrom: { fieldRef: { fieldPath: metadata.name } }
  - name: NODE_NAME
    valueFrom: { fieldRef: { fieldPath: spec.nodeName } }
  - name: MEMORY_LIMIT
    valueFrom: { resourceFieldRef: { containerName: app, resource: limits.memory } }

This is handy for log fields, metrics labels, and runtimes that need to size themselves from their limit.

Volumes and persistent storage

Containers forget everything when they restart. Volumes are how data outlives a container, a pod, or a node, and the storage abstractions are built to keep application teams and storage details apart.

Volumes are pod-level

A volume is declared in the pod spec and mounted into one or more of its containers. Its lifetime depends on its type:

Volume typeLives as long asTypical use
emptyDirThe pod (survives container restarts)Scratch space, sharing files between containers. medium: Memory makes it tmpfs, and that memory counts against the container’s limit.
configMap, secret, downwardAPI, projectedThe podConfig files, credentials, service account tokens
persistentVolumeClaimThe claim, independent of any podDatabases, uploads, anything durable
hostPathThe nodeNode agents only. In application pods it is a security risk and ties the pod to one node.

PersistentVolumes, claims and classes

Persistent storage is split into three objects so that the people who use storage and the people who run it do not need to know each other’s details:

  • A PersistentVolume (PV) is a cluster-scoped object representing a piece of real storage: an EBS volume, a GCE persistent disk, an NFS export, a local SSD.
  • A PersistentVolumeClaim (PVC) is a namespaced request: “I need 20Gi, ReadWriteOnce, of class fast.” Pods reference claims, never volumes.
  • A StorageClass describes how to create PVs on demand: which provisioner (CSI driver), what parameters (disk type, IOPS), the reclaim policy, whether volumes can be expanded, and when to bind.
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: { name: fast }
provisioner: ebs.csi.aws.com
parameters: { type: gp3 }
reclaimPolicy: Delete
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: uploads }
spec:
  storageClassName: fast
  accessModes: [ReadWriteOnce]
  resources: { requests: { storage: 20Gi } }

With dynamic provisioning, creating the claim causes the CSI driver to create a real disk and a matching PV, and the two are bound one-to-one. A PVC stuck in Pending means no PV matches and none could be provisioned; kubectl describe pvc says why.

volumeBindingMode matters

Cloud disks are zonal. With Immediate binding, the disk is created as soon as the claim exists, in whatever zone the provisioner picks. If the scheduler then wants to place the pod in another zone, the pod can never start there. WaitForFirstConsumer delays provisioning until a pod using the claim is scheduled, so the disk is created where the pod will run. Use it for any zonal storage. A bound PV carries node affinity for its zone, and the scheduler honours it from then on: the pod is pinned to that zone for life.

Access modes

ModeMeaning
ReadWriteOnce (RWO)Read-write by a single node. Several pods on that node can share it.
ReadWriteOncePod (RWOP)Read-write by a single pod in the whole cluster.
ReadOnlyMany (ROX)Read-only by many nodes.
ReadWriteMany (RWX)Read-write by many nodes. Needs a shared filesystem (NFS, EFS, Filestore, CephFS); block devices cannot do this.

Pitfall: RWO and rolling updates

A Deployment with one replica and an RWO volume does a rolling update by starting the new pod before stopping the old one. If the new pod lands on a different node, the disk is still attached to the old node, and the new pod hangs in ContainerCreating with a Multi-Attach error event. Meanwhile the old pod is waiting for the new one to become ready. Use strategy: Recreate for such Deployments, or better, a StatefulSet.

Reclaim policy: read this before deleting a PVC

When a claim is deleted, the PV’s persistentVolumeReclaimPolicy decides what happens to the real storage. Delete, the default for most dynamically provisioned classes, deletes the cloud disk. Retain keeps the PV and disk, marked Released, for an administrator to recover or clean up. For anything you would mourn, use a class with Retain, or patch the PV to Retain before risky operations, and have snapshots regardless. PVCs in use by a pod are protected by a finalizer (kubernetes.io/pvc-protection) and wait in Terminating until the pod is gone, which is one more reason a namespace deletion can hang.

CSI under the hood

Storage drivers are CSI (Container Storage Interface) plugins with two parts. A controller Deployment, with sidecars like external-provisioner, external-attacher, external-resizer and external-snapshotter, watches API objects and calls the storage backend: create disk, attach to node, expand, snapshot. A node DaemonSet does the work on each machine: format the device, mount it into the pod’s directory. Attachments show up as VolumeAttachment objects, which are useful when debugging a disk that will not detach.

Built on CSI: volume expansion (edit the PVC’s size, if the class allows it), VolumeSnapshot objects for point-in-time copies, and cloning a PVC from another or from a snapshot.

Stateful workloads, honestly

Running databases on Kubernetes is reasonable today, usually with an operator (CloudNativePG, the various MySQL and Kafka operators). Be clear about the failure behaviour, though. When a node dies, an RWO disk stays attached to it from the cloud’s point of view. Kubernetes waits for the node to be declared gone and then for a force-detach timeout before the disk can attach elsewhere. Failover for a single-instance database on a lost node can take many minutes. High availability for data comes from replication at the database level, with replicas spread across zones, not from Kubernetes moving one disk around. If your team does not want to own that, a managed database is a perfectly senior decision.

Identity, RBAC and admission

Every request to the API passes three gates: who are you, are you allowed, and is this object acceptable. Pods have a fourth: what can this process do on the node. Knowing which gate rejected you is half of any permissions problem.

Authentication: there are no user objects

Kubernetes has no User resource. Human identities come from outside and are presented with each request:

  • X.509 client certificates: the certificate’s CN is the username and its O fields are groups. The admin kubeconfig from kubeadm or kind works this way. Certificates cannot be revoked easily, so they are a poor fit for people.
  • OIDC tokens from an identity provider (Okta, Google, Entra ID, Dex), validated by the API server.
  • Cloud IAM via exec plugins in your kubeconfig (aws eks get-token, gke-gcloud-auth-plugin, kubelogin), which fetch short-lived tokens.

Workloads use ServiceAccounts, which are real namespaced objects. A pod runs as one (the namespace’s default unless set), and the kubelet mounts a projected token at /var/run/secrets/kubernetes.io/serviceaccount/token. That token is a JWT bound to the pod, limited to an audience, and expires after about an hour; the kubelet rotates it. Its username is system:serviceaccount:<namespace>:<name>. Long-lived Secret-based tokens are no longer created automatically. Set automountServiceAccountToken: false on pods that never call the API.

The same projected-token mechanism powers workload identity on clouds: EKS Pod Identity or IRSA, GKE Workload Identity, Azure Workload Identity exchange the pod’s token for cloud credentials, so pods get IAM permissions without stored keys.

kubectl auth whoami      # how the API server sees you: username and groups

kubeconfig anatomy

apiVersion: v1
kind: Config
clusters:                      # where: API endpoint and CA to trust
  - name: prod-eu
    cluster: { server: https://…, certificate-authority-data: … }
users:                         # who: credentials or a command that produces them
  - name: me@prod-eu
    user:
      exec: { apiVersion: client.authentication.k8s.io/v1beta1, command: aws, args: [eks, get-token, --cluster-name, prod-eu] }
contexts:                      # a named (cluster, user, default namespace) triple
  - name: prod-eu
    context: { cluster: prod-eu, user: me@prod-eu, namespace: shop }
current-context: prod-eu

kubectl and k9s both read this file (or every file listed in KUBECONFIG, merged). Switching context in k9s with :ctx switches between these entries.

Authorization: RBAC

RBAC has four objects. Roles (namespaced) and ClusterRoles (cluster-wide) list rules: API groups, resources, verbs, and optionally specific resource names. RoleBindings and ClusterRoleBindings grant a role to subjects: users, groups or ServiceAccounts.

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: pod-reader, namespace: shop }
rules:
  - apiGroups: [""]                       # "" is the core group
    resources: [pods, pods/log]
    verbs: [get, list, watch]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: oncall-read-pods, namespace: shop }
subjects:
  - { kind: Group, name: oncall, apiGroup: rbac.authorization.k8s.io }
roleRef: { kind: Role, name: pod-reader, apiGroup: rbac.authorization.k8s.io }

Things worth knowing:

  • RBAC is purely additive. There are no deny rules; permissions are the union of everything bound to you and your groups.
  • A ClusterRole bound with a RoleBinding grants those permissions only in the binding’s namespace. This is how you define a role once (the built-in view, edit, admin) and grant it per namespace.
  • Some verbs and resources are effectively escalation paths: escalate, bind and impersonate; creating pods (run as any ServiceAccount in the namespace, mount any Secret); nodes/proxy; write access to webhook configurations; wildcards. Audit for these first.
kubectl auth can-i delete pods -n shop
kubectl auth can-i --list -n shop
kubectl auth can-i get secrets -n shop --as=system:serviceaccount:shop:checkout
kubectl auth can-i create deployments -n shop --as=jane --as-group=oncall

A 403 Forbidden message names the user, verb, resource and namespace. Read it literally; it tells you exactly which rule is missing.

Admission control

After authorization, admission controllers can change or reject objects. The order is mutating admission, then schema validation, then validating admission. Many are built in and you rely on them daily: ServiceAccount (sets default service account and token volume), LimitRanger and ResourceQuota, DefaultTolerationSeconds (the 300-second tolerations from chapter 8), PodSecurity.

Policies are added in two ways. Admission webhooks are HTTPS services the API server calls for matching requests; policy engines such as Kyverno and OPA Gatekeeper, and sidecar injectors, work this way. ValidatingAdmissionPolicy, stable since v1.30, evaluates CEL expressions inside the API server with no webhook to run:

apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata: { name: require-registry }
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
      - { apiGroups: [apps], apiVersions: [v1], operations: [CREATE, UPDATE], resources: [deployments] }
  validations:
    - expression: "object.spec.template.spec.containers.all(c, c.image.startsWith('registry.example.com/'))"
      message: "images must come from registry.example.com"
# plus a ValidatingAdmissionPolicyBinding that selects which namespaces it applies to

Pitfall: the webhook that took down the cluster

A webhook with failurePolicy: Fail that matches pods in every namespace becomes a hard dependency of the whole cluster. If its pods are down, nothing can create pods anywhere, including the webhook’s own replacement pods and the system components that could fix it. Scope webhooks with namespaceSelector, exclude kube-system and the webhook’s own namespace, run several replicas with a PDB, and set tight timeouts.

Pod Security Standards

Three predefined levels describe how much a pod may do on its node: privileged (anything), baseline (blocks known privilege escalations such as host namespaces, privileged containers, most hostPath), and restricted (hardened: non-root, no privilege escalation, all capabilities dropped, seccomp required). The built-in Pod Security Admission enforces them per namespace through labels:

kubectl label ns shop \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/warn=restricted \
  pod-security.kubernetes.io/audit=restricted

A pod that meets restricted looks like this, and there is little reason for ordinary services not to:

spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    fsGroup: 10001
    seccompProfile: { type: RuntimeDefault }
  containers:
    - name: app
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true      # not required by restricted, but good practice
        capabilities: { drop: [ALL] }

The supply chain

Most real compromises arrive through what you run, not through the API. Pin images by digest or immutable tag, scan them, sign them (Sigstore cosign) and verify signatures at admission, pull only from registries you control or mirror, and keep base images small. Enable API server audit logging so you can answer “who did this” after the fact.

k9s, properly

k9s is a terminal UI over the same API kubectl uses. Most people learn five keys and stop. With a model of what it is doing and a few dozen bindings, it becomes the fastest debugger you have.

What k9s is

k9s reads your kubeconfig, connects as you, and opens watches on whatever resource type you are viewing. That has three consequences worth keeping in mind:

  • It can do exactly what your RBAC allows and nothing more. If a view is empty or an action fails, check permissions before suspecting k9s.
  • Lists are live. A pod changing state updates in place, so you can watch a rollout or a crash loop without re-running anything.
  • Every view is a generic table over an API resource, which is why it can show any type, including custom resources, without special support. If kubectl api-resources lists it, : plus its name opens it.

Actions like logs, shell and port-forward go through the API server to the kubelet, the same path as kubectl (chapter 3). If they hang while lists work, the node is usually unreachable from the control plane.

Starting it

k9s                          # current context and namespace
k9s -n shop                  # start in a namespace
k9s -A                       # all namespaces
k9s --context prod-eu        # a specific context
k9s -c deploy                # start on the deployments view
k9s --readonly               # disable every modifying action
k9s info                     # print where config, logs and skins live

Pitfall

Ctrl+k skips the shutdown sequence from chapter 5. The container gets no SIGTERM grace, and the API object is removed before the kubelet confirms the process stopped. On a StatefulSet pod whose node is unreachable, that can leave two copies running. Use Ctrl+d unless you know why you need a kill.

Workflows worth practising

Triage a crash loop in thirty seconds

  1. :po, then Ctrl+z to show only failing pods (or /!Running).
  2. d on the pod. Read the bottom Events first, then Last State for the reason and exit code. OOMKilled and exit 137 point at memory; a probe failure event points at probes; exit 1 points at the app.
  3. Esc, then p for the previous container’s logs: the crash itself is in the instance that died, not the one currently starting.
  4. If it is config, Enter on the owning Deployment through :xray deploy shows which ConfigMaps and Secrets it mounts; y on them shows what the pod actually received.

Find what is eating a node

:no, select the busy node, Enter to list its pods, then Shift+m or Shift+c. Compare usage with the requests columns in wide mode (Ctrl+w): pods using far more than they request are why the node is under pressure.

Check why a Service returns errors

:svc, select it, Enter. An empty pod list means a selector mismatch. Pods listed but not ready mean readiness probes are failing; d on one shows the probe errors. All ready but still failing? Shift+f on a pod to port-forward and hit it directly, which tells you whether the problem is the app or the path to it.

Watch a rollout

:deploy, select it, and keep it open: the ready and up-to-date columns move live. Enter shows pods from both ReplicaSets, and the age column shows which are new. :rs filtered by the app name shows the old and new ReplicaSets scaling against each other.

A debugging playbook

Most Kubernetes incidents fall into a small number of shapes. Recognising the shape from the symptom, and knowing which object holds the evidence, is what makes someone fast.

The method

Before any specific symptom, the same three questions resolve most problems:

  1. Where in the pipeline did it stop? Use the life of kubectl apply from chapter 3. Is the object missing (admission or quota)? Pod unscheduled (scheduler)? Scheduled but not started (kubelet, image, volumes, CNI)? Started but crashing (the app)? Running but not receiving traffic (readiness, Service, network)?
  2. What does the controller one level up say? Events and conditions on the Deployment, ReplicaSet, PVC or Node often explain what the pod cannot.
  3. What changed? kubectl rollout history, your Git log, recent node upgrades, a new admission policy. Most incidents follow a change.

Read events from the bottom up, newest last. Read the previous container’s logs, not the current one’s. Compare the live YAML with what you meant to deploy.

What to measure and alert on

Two frameworks cover most of it. For services, RED: rate, errors and duration (latency percentiles) of requests. For resources, USE: utilisation, saturation and errors of CPU, memory, disk and network. Google’s four golden signals (latency, traffic, errors, saturation) combine both.

Page on symptoms that users feel, ideally expressed as an SLO with burn-rate alerts (“we are spending our monthly error budget fast enough to run out in two days”). Do not page on causes like “a pod restarted” or “CPU is at 80%”: they are useful on dashboards and as low-urgency tickets, but they fire constantly without user impact and teach people to ignore pages.

Logs

Containers should write logs to stdout and stderr. The runtime writes them to files under /var/log/pods/ on the node, and the kubelet rotates them by size. kubectl logs reads those files through the kubelet, which has limits that surprise people:

  • Only the current and the immediately previous container instance are available.
  • When a pod is deleted or evicted, its logs go with it.
  • Rotation means a chatty service may only have minutes of history.

So every real cluster runs a log collector as a DaemonSet (Fluent Bit, Vector, the OpenTelemetry Collector, or a vendor agent) that tails those files, adds Kubernetes metadata (namespace, pod, labels), and ships them to a store such as Loki, Elasticsearch or a hosted service. Write structured logs (JSON) with a request or trace ID, so you can follow one request across services.

Events and traces

Kubernetes events (scheduling failures, probe failures, image pulls, evictions, scaling decisions) are stored as objects with a short retention, around an hour by default. Export them to your log system with an event exporter so they are available during postmortems.

Distributed tracing, usually with OpenTelemetry, records the path of a single request through many services with timings. It is the tool for “which of these twelve services made checkout slow.” Instrumentation is in the application; Kubernetes only needs to run the collector.

Autoscaling

Kubernetes scales on three levels: more pods, bigger pods, and more nodes. Each is a separate controller with its own delay, and the delays add up.

Horizontal Pod Autoscaler

The HPA adjusts a workload’s replica count (through its scale subresource) to keep a metric near a target. Every 15 seconds by default, it computes:

desiredReplicas = ceil( currentReplicas × currentMetricValue / targetMetricValue )

With 4 replicas averaging 90% CPU utilisation and a target of 60%, it wants ceil(4 × 90 / 60) = 6. If the ratio is within a tolerance of 1.0 (10% by default), it does nothing. With several metrics, it computes each and takes the largest.

The detail people miss: for CPU and memory, utilisation is measured relative to requests, not limits or node size. A pod requesting 100m and using 150m is at 150%. Requests set too low make the HPA scale out aggressively; set too high, it never scales. Right requests come first, autoscaling second.

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: checkout }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: checkout }
  minReplicas: 3
  maxReplicas: 30
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 60 } }
    - type: Pods                                   # custom per-pod metric via a metrics adapter
      pods:
        metric: { name: http_requests_in_flight }
        target: { type: AverageValue, averageValue: "20" }
  behavior:
    scaleUp:
      policies: [{ type: Percent, value: 100, periodSeconds: 30 }]   # at most double every 30s
    scaleDown:
      stabilizationWindowSeconds: 300               # the default: wait 5 minutes of lower demand
      policies: [{ type: Pods, value: 2, periodSeconds: 60 }]

Metric types: Resource (CPU, memory from metrics-server), ContainerResource (one container, ignoring sidecars), Pods and Object (custom metrics through an adapter such as prometheus-adapter), and External (queue length in a cloud service). CPU is a good default for CPU-bound services. For I/O-bound ones, requests in flight or queue depth reflect load far better.

Pitfall: two owners of replicas

If your Deployment manifest sets spec.replicas and an HPA also manages it, every deploy resets the count to the manifest’s number, and the HPA then fights it back. During a traffic peak, a routine deploy can cut capacity in half. Remove replicas from manifests of HPA-managed workloads (server-side apply makes this conflict visible, as in chapter 4).

Vertical Pod Autoscaler

The VPA watches actual usage and recommends, or applies, CPU and memory requests. Modes range from Off (recommendations only, which is a safe and very useful way to right-size) to modes that set requests when pods are created or update them on running pods, by eviction or in place on clusters that support in-place resize. Do not let the VPA and HPA both act on the same CPU or memory metric; they will chase each other. A common combination is HPA on a custom metric with VPA on resources, or VPA in recommendation mode only.

Event-driven scaling with KEDA

KEDA scales on event sources such as Kafka lag, SQS queue depth, Redis lists, Prometheus queries and cron schedules. It feeds external metrics to an HPA it manages, and it can scale a workload to zero and back up, which the HPA alone cannot. It is the standard tool for queue workers.

Scaling nodes

Pod autoscaling only helps if there is room. The Cluster Autoscaler watches for pods that are Pending because nothing fits, simulates which node group would fit them, and increases that group’s size. It removes nodes whose pods could fit elsewhere, respecting PDBs and pods that block removal (local storage, certain annotations). Karpenter, common on AWS and spreading elsewhere, skips node groups: it looks at pending pods and launches instances of whatever size and type fit them, and continuously consolidates the cluster onto fewer or cheaper nodes.

The end-to-end delay of a scale-out under load is worth writing down for your own system:

metric scraped (15–60s) → HPA evaluates (15s) → pods Pending
  → node provisioned and joins (often 45s–3min) → image pulled (seconds to minutes)
  → app starts and passes readiness → added to endpoints

Several minutes is normal. If your traffic can spike faster than that, you need headroom: a higher minReplicas, a lower utilisation target, or overprovisioning with low-priority placeholder pods that keep spare nodes warm and are preempted instantly when real pods need the space.

Shipping changes safely

Deploying to Kubernetes is easy. Deploying a hundred times a week without anyone noticing takes packaging, a source of truth, a rollout strategy and a short list of non-negotiable checks.

Packaging manifests

Raw YAML stops scaling the moment you have two environments. The two standard tools take different approaches:

Kustomize (built into kubectl apply -k) patches plain YAML. A base holds the common manifests, and overlays/staging and overlays/prod apply patches, set images and replicas, add labels, and generate ConfigMaps and Secrets with content hashes. No templating language, so what you see is valid Kubernetes YAML.

app/
  base/
    deployment.yaml  service.yaml  kustomization.yaml
  overlays/
    staging/kustomization.yaml     # namespace, image tag, smaller replicas
    prod/kustomization.yaml        # patches: resources, HPA, PDB

Helm renders Go templates with values into manifests, and tracks each install as a release (stored as Secrets in the namespace) with history and rollback. It is the standard for distributing third-party software, and charts can be configured heavily through values. The cost is templates that become hard to read and debug; use helm template and helm diff to see what will actually be applied.

A reasonable rule: Helm to install other people’s software, Kustomize (or a small, boring Helm chart) for your own services. Either way, review rendered output, not just templates.

GitOps

In a push model, CI runs kubectl apply or helm upgrade against the cluster. In GitOps, a controller inside the cluster (Argo CD or Flux) watches a Git repository and continuously reconciles the cluster to match it. That is the same declarative loop from chapter 1, applied one level up.

  • Git becomes the audit log and the approval process: changes arrive as reviewed pull requests.
  • Drift is detected and, if you allow it, reverted. A manual kubectl edit in production shows up as out of sync.
  • CI no longer needs cluster credentials, which removes a high-value secret.
  • Rebuilding a cluster is pointing a new controller at the same repository.

Typical flow: CI builds and pushes an image, then commits the new tag to the environment’s config (by pull request, or through an image updater), and the GitOps controller rolls it out. Promotion from staging to production is another commit.

Image references

Never deploy :latest or any tag that moves. With a mutable tag, you cannot tell what is running, a rollback to “the previous manifest” deploys the same tag and therefore the same broken image, and nodes that pull at different times may run different code. (Kubernetes also defaults imagePullPolicy to Always for :latest, adding a registry dependency to every pod start.) Use immutable tags such as the Git commit SHA, or pin by digest (image@sha256:…), and configure the registry to refuse tag overwrites.

The zero-downtime checklist

Each of these was covered in an earlier chapter. Together they are what make rollouts invisible to users:

  1. A readiness probe that reflects real ability to serve (chapter 5).
  2. Graceful shutdown: a preStop delay, SIGTERM handled with draining, and a grace period long enough for both (chapters 2 and 5).
  3. A rolling update with maxUnavailable: 0 or a value your capacity can absorb, plus minReadySeconds to catch pods that crash right after becoming ready (chapter 6).
  4. At least two replicas, spread across nodes and zones, protected by a PodDisruptionBudget that allows at least one disruption (chapter 8).
  5. Requests that reflect real usage, so new pods actually fit and are not throttled or evicted (chapter 7).
  6. Backward-compatible changes: every release must work alongside the previous one, because during a rolling update both serve traffic and share the database.
  7. Config changes that trigger rollouts, through hashed names or checksum annotations (chapter 11).

In production: schema changes

Rule 6 matters most for databases. Use expand and contract: first deploy a schema change that adds without breaking (new nullable column, new table), then deploy code that writes both and reads the new, then backfill, then deploy code that only uses the new, and only then remove the old column. Each step can be rolled back on its own. Run migrations as a separate Job or a pipeline step, not in an init container of every replica, where several copies race to migrate at once.

The distributed system

Kubernetes as a distributed system

Kubernetes is one of the most widely deployed distributed systems in the world, and its design choices are textbook answers to textbook problems. Understanding them makes you better at Kubernetes, and better at building your own systems on top of it.

Level-triggered, not edge-triggered

An edge-triggered system reacts to events: “a pod was deleted, so create one.” If the event is lost, because the controller was restarting or the network dropped a message, the reaction never happens. A level-triggered system reacts to state: “there should be three pods and I see two.” It does not matter how the state came about or how many events were missed; the next look at the world gives the right answer.

Kubernetes controllers use events only as a hint about when to look, and always decide what to do from the full current state. They also resync periodically even without events. This is why the system heals from controller crashes, API server restarts and network blips without any special recovery code. It also imposes a discipline: reconcile functions must be idempotent. Running one twice in a row with the same state must be harmless, because it will happen.

List, watch and informers

Controllers do not poll the API server. They use list-watch:

  1. List all objects of a type. The response carries a collection resourceVersion, a point in the history of etcd.
  2. Watch from that resourceVersion. The server streams ADDED, MODIFIED and DELETED events in order, plus periodic BOOKMARK events that advance the resourceVersion.
  3. If the connection drops, re-watch from the last resourceVersion seen. If that version is too old (etcd compacts its history), the server answers 410 Gone and the client must list again.

The API server keeps a watch cache in memory so thousands of watchers do not each hit etcd. Client libraries wrap all of this in an informer: list-watch, plus a local in-memory cache of every object (indexed, for example by namespace or label), plus event handlers. Handlers do not do work directly. They push the object’s key (namespace/name) onto a work queue, which deduplicates keys and retries failures with exponential backoff. Workers pop keys, read the current object from the cache, and reconcile.

API server ──list/watch──▶ informer cache ──event──▶ work queue (dedup, backoff)
                                  ▲                          │
                                  └──── read current state ◀─┤ worker: reconcile(key)
API server ◀──────────── writes (create/update/patch) ───────┘

Two consequences matter in practice. Controllers read from a cache that can be slightly stale, so they must tolerate acting on old information. And writes are checked by the API server with optimistic concurrency, which catches exactly that staleness.

Optimistic concurrency

Every object carries a resourceVersion. An update sends the version the client read; if the stored object has changed since, the API server rejects it with 409 Conflict. The client re-reads, re-applies its change, and retries. This is compare-and-swap, built on etcd’s transactional revisions, and it means two controllers or two engineers can never silently overwrite each other’s change. No locks are held, so a slow client never blocks anyone. Your own code that updates Kubernetes objects must handle 409 with a retry loop (client-go’s RetryOnConflict exists for this), or use server-side apply, which merges by field ownership instead.

etcd and consensus

etcd replicates its data with Raft. One member is elected leader; writes go to the leader, which appends them to its log and replicates them to followers. An entry is committed once a majority (a quorum) has persisted it. If the leader fails, followers that stop hearing heartbeats start an election, and a candidate with an up-to-date log wins a majority vote.

More members also make every write slower, since more acknowledgements are needed, so five is the usual maximum. The majority rule is what prevents split brain: in a network partition, at most one side can have a majority, so at most one side can accept writes. The minority side becomes read-only or unavailable. etcd chooses consistency over availability in a partition, which is the right choice for the source of truth.

etcd is sensitive to disk latency (each commit needs an fsync on a majority of members) and has size limits: objects are capped at about 1.5 MiB per request, and the database has a storage quota. Huge ConfigMaps, thousands of stale Events and very large numbers of objects are the usual ways to stress it. Back it up with etcdctl snapshot save if you run your own control plane, and test restoring.

Leader election with Leases

The scheduler and controller-manager run several replicas for availability, but only one may act at a time, or two would fight over the same objects. They elect a leader through a Lease object in kube-system: whoever holds the lease renews it every few seconds; if renewals stop for the lease duration, another replica acquires it using an optimistic-concurrency update, so only one can succeed. Your own controllers can use the same mechanism (controller-runtime has it built in), and so can application singletons such as a scheduler for periodic tasks.

Lease-based leadership has a classic weakness: a leader that pauses (a long garbage collection, a frozen VM) may resume believing it still leads after another replica took over. Leader election helps you avoid duplicate work, but for operations that must never happen twice, the target system needs its own protection, such as fencing tokens or conditional writes.

What happens in a partition

Suppose a worker node loses its connection to the control plane but keeps running. Walk through it:

  1. The node’s kubelet stops renewing its Lease. After the node monitor grace period (tens of seconds), the node lifecycle controller marks it Unknown and taints it unreachable.
  2. After the 300-second default toleration, pods on it are marked for deletion. They cannot actually be confirmed stopped, because nobody can reach the kubelet.
  3. For a Deployment, the ReplicaSet does not count terminating pods, so it immediately creates replacements elsewhere. Meanwhile the old pods may still be running on the isolated node, perhaps still serving traffic from clients on its side of the partition. For a while, there are more copies than you asked for. Deployments give you at least N replicas, not exactly N.
  4. For a StatefulSet, the controller will not create a new db-0 while the old db-0 object still exists, because two pods with the same identity might both write to what they believe is their data. It waits. The pod stays Terminating until the node returns or a human confirms it is gone. StatefulSets give you at most one pod per identity.

Pitfall: force-deleting StatefulSet pods

kubectl delete pod db-0 --force --grace-period=0 on a pod from an unreachable node tells Kubernetes “trust me, it is dead.” If it is not, you now have two db-0s, and possibly two writers on replicated storage. Before force-deleting, make sure the node is really off (shut down the VM, or delete the Node object once the machine is confirmed gone). Kubernetes also supports marking a node as out of service with the node.kubernetes.io/out-of-service taint, which lets it clean up pods and volume attachments safely once you have confirmed the node is down.

Eventual consistency you will meet

  • Endpoints lag. A pod that fails readiness is removed from Services on each node at slightly different times (chapter 5).
  • Cache staleness. A controller may act on an object version that has already changed. Status can lag spec, which is what observedGeneration tells you.
  • DNS caching. Clients and resolvers cache answers; a headless Service’s pod list is only as fresh as the TTL and the client’s own caching.
  • Config propagation. Mounted ConfigMap changes arrive at different pods at different times, so for a while some pods run the old config and some the new.

Design for these windows rather than wishing them away: make handlers idempotent, version your config and messages, and tolerate a mix of old and new during any change.

Failure patterns in services on Kubernetes

Kubernetes keeps processes running. It does not stop your services from failing as a system. These patterns cause most of the hard outages:

  • Retry storms. A slow dependency causes timeouts; every client retries; load multiplies exactly when the dependency is weakest. Use timeouts shorter than the caller’s, a small retry budget, exponential backoff with jitter, and circuit breakers.
  • Thundering herds. After a restart or a cache flush, every instance reconnects or refills its cache at the same moment. Stagger startup work, use request coalescing, and warm caches before readiness passes.
  • Cascading failure through health checks. Liveness probes that depend on downstream services turn one dependency’s trouble into restarts everywhere (chapter 5).
  • Metastable failures. A system pushed into overload by a brief spike stays overloaded after the spike ends, because the work generated by the overload (retries, timeouts, queue backlogs) keeps it saturated. Load shedding and bounded queues let it recover.
  • Correlated failure. Three replicas in one zone, all on one node type, all on the same bad config, fail together. Spread, stage rollouts, and canary config as carefully as code.

Custom resources and operators

Kubernetes lets you add your own object types and your own controllers, and they get everything built-in types get: the API, RBAC, kubectl, k9s, watches and GitOps. This is how most of the ecosystem is built.

CustomResourceDefinitions

A CRD registers a new resource type with the API server. Once applied, the server stores objects of that type in etcd, validates them against the schema, and serves them at /apis/<group>/<version>/…. On its own, a CRD does nothing else; it is a typed, validated, watchable place to put desired state.

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata: { name: websites.example.com }
spec:
  group: example.com
  scope: Namespaced
  names: { kind: Website, plural: websites, singular: website, shortNames: [web] }
  versions:
    - name: v1
      served: true
      storage: true
      subresources: { status: {} }            # spec and status written separately
      additionalPrinterColumns:
        - { name: Domain, type: string, jsonPath: .spec.domain }
        - { name: Ready,  type: string, jsonPath: ".status.conditions[?(@.type=='Ready')].status" }
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              required: [domain, replicas]
              properties:
                domain:   { type: string }
                replicas: { type: integer, minimum: 1, maximum: 20 }
              x-kubernetes-validations:
                - rule: "self.domain.endsWith('.example.com')"
                  message: "domain must be under example.com"
            status:
              type: object
              x-kubernetes-preserve-unknown-fields: true

After this, kubectl get websites, kubectl explain website.spec and :websites in k9s all work, with your printer columns.

Operators

An operator is a CRD plus a controller that encodes operational knowledge: how to deploy, scale, upgrade, back up and fail over a particular piece of software. A Postgres operator turns “I want a three-instance cluster with daily backups” into StatefulSets, Services, Secrets, replication configuration and backup Jobs, and keeps them correct as things fail.

Most operators are written in Go with controller-runtime, often scaffolded by kubebuilder or Operator SDK. The core is a reconcile function, and it follows every lesson from chapter 20:

func (r *WebsiteReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    var site examplev1.Website
    if err := r.Get(ctx, req.NamespacedName, &site); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)  // deleted: nothing to do
    }

    // Deletion: clean up external things, then release our finalizer.
    if !site.DeletionTimestamp.IsZero() {
        if err := r.deleteDNSRecord(ctx, &site); err != nil {
            return ctrl.Result{}, err                     // retried with backoff
        }
        controllerutil.RemoveFinalizer(&site, finalizerName)
        return ctrl.Result{}, r.Update(ctx, &site)
    }
    if controllerutil.AddFinalizer(&site, finalizerName) {
        if err := r.Update(ctx, &site); err != nil {      // persist the finalizer first
            return ctrl.Result{}, err
        }
    }

    // Desired child objects, owned by the Website so they are garbage-collected with it.
    deploy := r.desiredDeployment(&site)
    controllerutil.SetControllerReference(&site, deploy, r.Scheme)
    if err := r.Patch(ctx, deploy, client.Apply, client.FieldOwner("website-controller"), client.ForceOwnership); err != nil {
        return ctrl.Result{}, err
    }

    // Report what we observed, tied to the generation we acted on.
    site.Status.ObservedGeneration = site.Generation
    meta.SetStatusCondition(&site.Status.Conditions, metav1.Condition{
        Type: "Ready", Status: metav1.ConditionTrue, Reason: "Reconciled", ObservedGeneration: site.Generation,
    })
    return ctrl.Result{}, r.Status().Update(ctx, &site)
}

The patterns to notice: it reads current state and computes the full desired state every time (level-triggered, idempotent); it uses server-side apply for children so repeated runs converge; owner references give automatic cleanup of in-cluster children; a finalizer guards cleanup of things outside the cluster; errors are returned so the work queue retries with backoff; and status reports conditions with observedGeneration, the convention that tools like kubectl wait --for=condition=Ready and Argo CD understand.

When not to write one

An operator is software you now maintain forever, with its own upgrades, CRD version migrations, RBAC and failure modes. If a Helm chart or a few Kustomize overlays produce the right objects, and nothing needs to react to the running state afterwards, you do not need a controller. Write an operator when there is ongoing operational logic: failover, backups, coordinated upgrades, reacting to external systems. Before writing one, check whether a mature operator already exists.

A related warning: every CRD and controller you install is something that can break the cluster. Webhooks fail closed, controllers can hammer the API server with list calls, and CRDs with huge objects stress etcd. Treat installing an operator as adding a dependency to your control plane.

Running clusters in production

The last layer of experience is the unglamorous one: upgrades, tenancy, recovery and cost. These are the topics where a senior engineer’s judgement shows most.

Upgrades

Kubernetes ships about three minor releases a year, and each is supported for roughly fourteen months upstream. Managed providers have their own windows, sometimes with paid extended support. If you do not upgrade continuously, you end up doing several painful upgrades at once under deadline.

The rules:

  • Upgrade the control plane first, one minor version at a time (1.33 → 1.34, never 1.33 → 1.35).
  • Then nodes. The kubelet may be up to three minor versions older than the API server but never newer. That skew window is what allows the control plane and nodes to be upgraded separately.
  • Before each upgrade, check for removed APIs. Deprecated versions (an old v1beta1 of something) eventually stop being served, and manifests or Helm charts using them fail to apply. Tools like pluto and kubent scan for them, and API server metrics show which deprecated APIs are still being called.
  • Upgrade add-ons (CNI, CSI drivers, ingress or gateway controllers, cert-manager, operators) against their compatibility matrices. These break more upgrades than Kubernetes itself does.
  • Replace nodes rather than upgrading them in place where you can: add new nodes on the new version, cordon and drain old ones, delete them. PDBs and spread constraints from chapter 8 are what keep this invisible.

Many organisations end up with a few clusters per environment and region rather than one giant cluster, because a cluster is also a blast radius.

Backup and disaster recovery

Separate what you need to recover:

  • Cluster state (objects): an etcd snapshot restores everything at once, but only to an identical control plane. Tools like Velero back up resources through the API and can restore selected namespaces into a different cluster. With GitOps, most of this state is already in Git and the cluster can be rebuilt by pointing a controller at the repository.
  • Application data: lives in PersistentVolumes and external databases. Back it up with volume snapshots, Velero with a snapshot or file-level plugin, or the database’s own tools, which are usually best because they produce consistent backups.
  • Things outside the cluster: DNS, cloud IAM, load balancer configuration, secrets in external stores, container images in your registry.

A backup that has never been restored is a hope. Rebuilding a staging cluster from scratch on a schedule is the most honest test of your recovery story.

Cost

You pay for nodes, and node count is driven by requests, not usage. A cluster where pods request four times what they use costs four times what it needs to. The levers: right-size requests using VPA recommendations or usage percentiles; let the cluster autoscaler or Karpenter remove empty capacity; bin-pack with fewer, larger nodes where failure domains allow; use spot or preemptible nodes for interruption-tolerant workloads; and scale non-production environments down outside working hours. Make cost visible per namespace or team (OpenCost or the provider’s tools), because people optimise what they can see.

Questions a senior engineer can answer

Answer each out loud before opening it. If you can explain all of them clearly, including the why, you understand Kubernetes at the level of someone who has run it in production for a couple of years.

  1. A pod is deleted from a Deployment. Name every component involved in replacing it and serving traffic again.
    Answer

    API server (records deletion), kubelet (runs preStop, SIGTERM, cleans up), EndpointSlice controller (marks it not ready), kube-proxy on all nodes (removes it from rules), ReplicaSet controller (sees fewer live pods, creates one), scheduler (binds it), kubelet on the new node (runtime, CNI, probes), EndpointSlice controller again (adds it once ready), kube-proxy again. None calls another; each reacts to API changes.

  2. Why do pods sometimes take exactly 30 seconds to terminate?
    Answer

    PID 1 ignores SIGTERM, usually a shell-form entrypoint or an app without a handler, so the kubelet waits the default 30-second grace period and sends SIGKILL.

  3. Your service returns errors for a few seconds during every deploy. Walk through the causes in order of likelihood.
    Answer

    The endpoint-removal race (no preStop delay), the app exiting immediately on SIGTERM without draining, missing or optimistic readiness probes letting traffic in too early, maxUnavailable removing capacity, long-lived connections not being closed, and incompatible versions running side by side.

  4. What is the difference between requests and limits, for CPU and for memory?
    Answer

    Requests are used for scheduling and as a relative share under contention (CPU weight). Limits are enforced by cgroups: exceeding a CPU limit throttles the container within each 100ms period; exceeding a memory limit gets it OOM-killed. CPU is compressible, memory is not.

  5. A service has low average CPU but bad p99 latency and a 1-core CPU limit. What do you check?
    Answer

    CFS throttling: the ratio of throttled periods to total periods. Multi-threaded processes can exhaust the quota early in each period. Then decide whether to raise or remove the limit, and whether the runtime’s thread count matches the CPU budget.

  6. A pod shows Evicted. How is that different from OOMKilled?
    Answer

    OOM kill: the kernel kills one container that exceeded its own memory limit; the container restarts in the same pod. Eviction: the kubelet removes whole pods because the node is under memory, disk or PID pressure; the pod is gone and the controller replaces it elsewhere. Evictions point to requests that underestimate real usage.

  7. Why can a Deployment briefly run more replicas than you asked for, but a StatefulSet never runs two copies of the same pod?
    Answer

    The ReplicaSet does not count terminating pods and creates replacements immediately, so during a partition or slow shutdown, old and new can coexist (at least N). The StatefulSet controller will not create name-0 until the old name-0 object is fully gone, because identity and storage must be unique (at most one). This is why force-deleting StatefulSet pods on unreachable nodes is dangerous.

  8. Why are control planes three or five nodes?
    Answer

    etcd uses Raft, which commits writes with a majority. Three tolerate one failure, five tolerate two; four tolerates only one, like three, while making writes slower. Odd sizes maximise fault tolerance per member, and the majority rule prevents split brain.

  9. What does level-triggered mean, and why does it make controllers robust?
    Answer

    Controllers decide what to do from current state, not from the events that led to it. Missed events, restarts and duplicate deliveries do not matter, because the next reconcile sees the full picture. It requires reconcile logic to be idempotent.

  10. What is resourceVersion for?
    Answer

    Optimistic concurrency (updates with a stale version get 409 Conflict) and resuming watches from a point in history (with 410 Gone if it is too old and a relist is needed). It is opaque and must not be compared numerically.

  11. A namespace is stuck in Terminating. How do you approach it?
    Answer

    Read the namespace’s status conditions, which list remaining resources and finalizers. Find the objects that still exist and the finalizers blocking them. Usually a controller that should remove a finalizer has been uninstalled, or an aggregated API (such as a broken metrics API) cannot be listed. Fix the controller if possible; remove finalizers by hand only after understanding what cleanup will be skipped.

  12. Why can gRPC traffic to a Kubernetes Service end up badly unbalanced?
    Answer

    kube-proxy balances connections, not requests. gRPC multiplexes all requests over one long-lived HTTP/2 connection, so each client sticks to one pod. Use client-side balancing over a headless Service, an L7 proxy or mesh, or limit connection age.

  13. What does ndots:5 do and when does it hurt?
    Answer

    Names with fewer than five dots are first tried with each search domain appended. External names like api.vendor.com trigger several failed cluster lookups (A and AAAA each) before the real one, multiplying DNS load and adding latency. Use trailing dots, lower ndots per pod, or a node-local DNS cache.

  14. Your NetworkPolicy allows traffic from namespace X, but pods in every namespace can now connect. What happened?
    Answer

    Most likely the namespaceSelector and podSelector were written as two separate list items (OR) instead of one item (AND), or an empty selector matched everything. Also check the CNI actually enforces policies.

  15. Who can read Secrets in a namespace, beyond those with explicit Secret permissions?
    Answer

    Anyone who can create pods, or anything that creates pods (Deployments, Jobs, CronJobs, StatefulSets) in that namespace, because they can mount any Secret there. Plus anyone with access to etcd or its backups if encryption at rest is off.

  16. An admission webhook is down. What breaks, and how do you prevent it?
    Answer

    With failurePolicy: Fail, every request it matches is rejected, potentially all pod creation cluster-wide, including the webhook’s own pods. Prevent it with namespace selectors excluding system namespaces, replicas with a PDB, short timeouts, and in-process ValidatingAdmissionPolicy where possible.

  17. HPA and a GitOps tool keep fighting over replicas. Why, and what is the fix?
    Answer

    The manifest sets spec.replicas, so every sync resets what the HPA chose. Remove replicas from manifests of autoscaled workloads (or tell the GitOps tool to ignore that field), so the HPA is the only owner.

  18. Why might an HPA targeting 60% CPU never scale out under heavy load?
    Answer

    Utilisation is relative to requests. If requests are high, or the CPU limit throttles the pod below the target, utilisation never reaches 60%. Also check that metrics-server works, that the metric applies to the right container, and that maxReplicas is not already reached.

  19. A PVC is Pending and its pod is Pending. Where do you look?
    Answer

    With WaitForFirstConsumer, the claim waits for the pod to be scheduled, so look at the pod’s scheduling events first. Otherwise describe pvc: no default StorageClass, provisioner errors, quota, or zone constraints. If a bound PV exists in another zone, the pod cannot be placed where the volume is.

  20. What happens to running workloads if the entire control plane goes down for ten minutes?
    Answer

    Running pods keep running and serving; kubelets keep containers alive and restart them locally; kube-proxy rules stay in place. Nothing can change: no scheduling, no scaling, no replacement of pods on failed nodes, no endpoint updates, no new deploys. The data plane is designed to keep working without the control plane, just frozen.

Glossary

Short definitions of the terms used throughout the guide, in the sense Kubernetes uses them.

Admission controller
Code that inspects, changes (mutating) or rejects (validating) API requests after authorization and before the object is stored.
Allocatable
The part of a node’s capacity available to pods, after reservations for the system, the kubelet and the eviction threshold.
Annotation
Non-identifying key/value metadata on an object, for tools and people. Not selectable.
CNI
Container Network Interface: the plugin contract that gives pods network interfaces and IPs.
Condition
A typed status entry (type, status, reason, message) such as Ready or Available, used to report an object’s state.
Controller
A loop that watches objects and acts to make actual state match desired state.
CRD
CustomResourceDefinition: registers a new resource type with the API server.
CRI
Container Runtime Interface: the gRPC contract between the kubelet and a container runtime such as containerd.
CSI
Container Storage Interface: the plugin contract for provisioning, attaching and mounting storage.
DaemonSet
Runs one pod on each (selected) node.
Deployment
Manages ReplicaSets to run interchangeable replicas with rolling updates and rollback.
EndpointSlice
An object listing the network endpoints (pod IPs, ports, readiness) behind a Service.
etcd
The strongly consistent, Raft-replicated key-value store holding all cluster state.
Eviction
Removing a pod from a node: voluntarily through the Eviction API (respecting PDBs), or by the kubelet under node pressure.
Finalizer
A string on an object that blocks its deletion until a controller performs cleanup and removes it.
Gateway API
The role-oriented successor to Ingress: GatewayClass, Gateway and route resources.
Generation
A counter on an object that increments when its spec changes. Compared with status.observedGeneration.
Headless Service
A Service with clusterIP: None; DNS returns pod IPs directly.
Informer
A client-side list-watch with a local cache and event handlers, the building block of controllers.
Ingress
The original, now frozen API for HTTP routing into a cluster, implemented by an ingress controller.
kube-proxy
The node component that programs rules sending Service virtual IP traffic to pod IPs.
kubelet
The node agent that runs pods through the container runtime and reports their status.
Label / selector
Identifying key/value pairs on objects, and queries over them that link objects loosely.
Lease
A lightweight object used for node heartbeats and leader election.
Namespace
A scope for names and the attachment point for most policy. Not a network boundary on its own.
NetworkPolicy
Allow-list rules for pod traffic, enforced by the CNI plugin.
Node affinity
Rules attracting pods to nodes by node labels, required or preferred.
Operator
A CRD plus a controller that encodes how to run a particular piece of software.
Owner reference
Metadata linking a dependent object to its owner, used for garbage collection.
PDB
PodDisruptionBudget: limits how many pods of a workload voluntary evictions may take down at once.
Pod
The smallest schedulable unit: containers sharing a network namespace and volumes on one node.
PV / PVC / StorageClass
A piece of storage, a namespaced request for storage, and the recipe for provisioning storage on demand.
QoS class
Guaranteed, Burstable or BestEffort, derived from requests and limits; decides eviction order.
Raft
The consensus algorithm etcd uses: a leader replicates a log and commits entries once a majority persists them.
Readiness
Whether a pod should receive traffic now. Not ready pods are removed from Service endpoints but not restarted.
Reconciliation
Comparing desired and actual state and acting to close the difference, repeatedly.
ReplicaSet
Keeps a fixed number of pods matching a selector running.
resourceVersion
An opaque version of an object, used for optimistic concurrency and resuming watches.
Server-side apply
Declarative updates merged by the API server with per-field ownership tracked in managedFields.
Service
A stable virtual IP and DNS name for a set of pods chosen by a selector.
ServiceAccount
An in-cluster identity for workloads, with short-lived projected tokens.
Sidecar
A helper container running alongside the main one; natively, an init container with restartPolicy: Always.
StatefulSet
Runs pods with stable names, DNS identities and per-pod storage, in order.
Taint / toleration
A node marking that repels pods, and a pod’s permission to ignore that marking.
Topology spread constraint
A rule limiting how unevenly a workload’s pods may be spread across zones, nodes or other domains.
Watch
A streaming API request that delivers changes to objects from a given resourceVersion onward.
